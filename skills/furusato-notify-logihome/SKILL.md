# furusato-notify-logihome — ロジホームの未出荷を正にして出荷完了通知を送る

`furusato-shiftplus` の §6(通知CSVの作り方)の上位の流れ。**ロジホームでまだ「出荷依頼」のままの行を、
通知が必要な件の正**にする(従来はローカルの `sent/` と通知済みの印だけで判断していたため、
アップロードの失敗や印とのずれを拾えなかった)。作業フォルダは `052.卸売注文GoQ統合`。

## 決まっていること(2026-10-15 ユーザー決定)

| 項目 | 決定 |
|---|---|
| 通知できる行 | ローカルの受注と1対1に結べ、**GoQに12桁の伝票番号がある行**。GoQの状態の文言(「作業中5」等)は見ない |
| 出荷予定日 | **GoQの「出荷日」**を読んで使う(空・読めないときだけ `--default-ship-date`)。違う日が混ざれば一覧に出す |
| ロジホームへの取込 | 配送業者**「その他（汎用）」**・ファイルを選び**「取り込みデータ確認」を押すところまで**がClaude。**「取り込み実行」(確定)は人が押す** |
| 書き込み | ツールはGoQにもロジホームにも書かない(出力CSVと計画JSON・推移ログだけ) |

## 手順

### 1. 未出荷CSVを取得する(ロジホーム)

- **Claude in Chrome を使う**(ユーザーのChromeのオートコンプリートでID・パスワードが入る。内蔵ブラウザには保存済みの情報が無い)。
  `https://kure.lhcloud.jp/login.php` を開き、入っていることを確認して**ログインボタンだけ押す**。ID・パスワードをClaudeが入力しない
- ログイン後の一覧(`/seller/delivery/`)で、「保存した検索条件」の**`未出荷`**を選ぶと、配送ステータス＝出荷依頼で自動検索される(件数が「全N件」に出る)。
  **前回の検索が残っていて、開いた時点ですでに「未出荷」で絞られていることがある**(2回目は選ぶ操作が不要だった)。「保存した検索条件」が `未出荷`、配送ステータスが `出荷依頼`、件数が「全N件」になっていることを画面で確かめる
- **表の見出しの「選択」ボタン**(「全解除」の上)を押すと全件が選択される(スライダーは使わない)。「選択中N件」を確認
- 「データ出力」(形式は CSV形式のまま)→ **「選択データを出力する」**。ダイアログは動くので、押す前に位置を確かめる
- ダウンロードフォルダに `sell_YYYYMMDDHHMM.csv`(CP932・53列)ができる。**ダウンロードは、そのつどユーザーの了承を取る**
- Chromeのスクリーンショットは、タブが背面だと30秒で timeout することがある。もう一度撮る

### 2. 照合して通知CSVを組み立てる(読み取りだけ)

```bash
python tools/notify_plan_from_logihome.py "C:/Users/user/Downloads/sell_YYYYMMDDHHMM.csv" --default-ship-date YYYY-MM-DD
```

出力の見方:

- `未出荷の推移: 前回の時刻 N件 → 今回の時刻 M件 (±差)` — `state/logihome_unshipped_trend.jsonl` に1CSVにつき1行たまる(日付別の内訳つき)
- `通知する X 行 / 除外 Y 行` — 通知CSVは `reports/シフトプラス出荷完了_<時刻>.csv`、計画は同名の `.plan.json`
- 除外の理由: 「ローカルに受注がありません(GoQ未登録)」=新しい寄附でまだ登録していない(→ `furusato-shiftplus` で登録) /
  「GoQに12桁の伝票番号がありません」=送り状が未発行 / 「受注伝票のみの注文」=対象外(送り状は代行会社から別送)
- 同じ伝票番号が複数の配送Noに付くのは**正常**(GoQが同じ寄附者の注文を1つの送り状に同梱した)。ロジホームには配送Noごとに同じ番号を通知する

### 3. 承認(アーティファクト)

通知する行・除外する行・出荷予定日の内訳・同じ伝票番号が複数行になるものを、**アーティファクトで見せる**(生成日時を見出し直下に)。
CSVは `C:\Users\user\Downloads\` と `\\192.168.1.50\共有スペース\寺下\999.一時ファイル\`(フォルダであることを確認してから)の両方へ置く。

### 4. ロジホームの取込画面を確認画面まで進める

- 一覧画面の「出荷データ取込」のダイアログは**iframeで、Chromeの操作が届かない**。`https://kure.lhcloud.jp/seller/delivery/modal/import.php` を**単独のページとして開く**
- 配送業者「**その他（汎用）**」のラジオを選ぶ → `file_upload` で通知CSVを選ぶ → **「取り込みデータ確認」**を押す
- 確認画面に「全N件 / 取り込み件数：N件」と、配送No・伝票番号・配送業者・出荷予定日・**お名前・住所**が並ぶ(名前・住所はロジホームが配送No.から引く。結べている裏づけ)。件数と日付を確かめて報告する
- **「取り込み実行」は押さない。**Chromeのタブをその画面のまま止め、ユーザーに確認と確定を頼む

### 5. 確定後の事後検証

確定の後、手順1で**未出荷CSVを取り直す**(通知した行が「出荷依頼」から消えているはず)。

```bash
python tools/notify_plan_from_logihome.py --mark reports/シフトプラス出荷完了_<時刻>.plan.json --after-csv "C:/Users/user/Downloads/sell_<取り直し>.csv"           # 確認(書かない)
python tools/notify_plan_from_logihome.py --mark reports/シフトプラス出荷完了_<時刻>.plan.json --after-csv "C:/Users/user/Downloads/sell_<取り直し>.csv" --apply   # 消えた受注にだけ通知済みの印
```

まだ「出荷依頼」のままの配送Noがある受注には印を付けず、理由を表示する(アップロードが一部落ちた等)。

取り直したCSVにも、手順2の照合をそのまま行う(推移ログが1行増え、前回との差が出る)。通知する行が0件なら、**CSVは作られない**
(空のCSVを取込と取り違えないため)。「通知する 0 行」「除外=ローカル未登録」だけなら、通知は完了している。

**2026-10-15 の実績(流れの確認)**: 未出荷 106件(20:36) → 6件(21:40)(−100)。通知した82受注すべてが消えたのを確かめて印を付けた。
sent/ のあられ(registered)140件は、全件に通知済みの印がある。残る6行は新しい寄附でGoQ未登録(あられ4行[うち2行 `_OLD`]・あられ以外2行)。

### 6. GoQのステータスを「処理済」へ移す(出荷済みの案件・2026-10-16 追加)

通知が済んだ(`shiftplus_reported_at` あり)・GoQに12桁の伝票番号がある受注は、GoQで「**作業中5**」のまま残る。これを「**処理済**」へ移す
(GoQの選択肢の表記は**「処理済」**。「処理済み」ではない)。受注伝票のみ(`slip_only`)は、すでに「処理済」なので対象外。

```bash
python tools/goq_move_status.py plan --out reports/goq_move_status_plan_<日付>.json          # GoQを読むだけ(約10分)
python tools/goq_move_status.py apply <plan.json>                                            # 何を書くかの表示だけ
python tools/goq_move_status.py apply <plan.json> --limit 1 --apply                          # 1件だけ書く → GoQを読み直して確認
python tools/goq_move_status.py apply <plan.json> --only-single --apply                      # 単品の受注(これまでと同じ動き)
python tools/goq_move_status.py apply <plan.json> --allow-changed-prefix dealorderdatesel_deal --apply   # 同梱で複数品の受注
```

- **計画をアーティファクトで見せて承認を得てから** `--apply`(GoQへの本番書き込み)。**先に1件→読み直し→残り**
- 1件ごとに `set_order_fields.py` が、今の状態・画面の受注番号を確かめてから書き、保存の前後で全入力欄を比べて、ステータス以外が変われば止める(変更前の値は `047.../probe_out/` に退避)
- **同梱で複数品の受注は、「処理済」にすると商品行の「発注日」に当日が自動で入る**(GoQの動き。単品では起きない)。2026-10-16 はユーザーが了承して
  `--allow-changed-prefix dealorderdatesel_deal` で許した。了承なしに許さない(ツールは止まる)
- 受注番号が合わないときは、同梱で統合された受注の元の番号(`<番号>-1`,`-2`…)を順に試す
- 終わったら、全件をGoQで読み直し、「処理済」になっていること・伝票番号と配送会社が変わっていないことを確かめる
- 実績(2026-10-16): 82受注(単品71+同梱11)を移動。読み直しで処理済82・異常0

## 罠

- **「配送No」列はロジホームの配送No.**(GoQの受注番号ではない)。`furusato-shiftplus` §6 と同じ
- 出荷が過去の日付なら、通知はそれだけ遅れている(ロジホームでは出荷依頼のまま)。件数と日付を必ず報告する
- GoQの状態文言だけで出荷済みと判断しない(`furusato-shiftplus` §7)。伝票番号の有無で判断する
- 新しい寄附(除外行)を放置しない。登録 → 送り状 → 次回の通知、の順で進む
- 取込の確定はユーザーの操作。Claudeは押さない(`LIMIT`として台帳に記録する)
