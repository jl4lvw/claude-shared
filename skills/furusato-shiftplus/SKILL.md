## 2. 「1行=1受注=1送り状」— 数量合算は絶対にしない

**同一商品コードの複数行も合算しない**(2026-09-02、有本様の実例で発覚。2026-09-07、
高橋様でも同型の実例あり)。シフトプラス管理画面(出荷依頼管理)側でも、同じ商品を
複数個寄附された場合は複数行として別掲される。`furusato_shiftplus_csv.py`は行ごとに
`qty=1`のitemを積むだけで、コードが同じでもマージしない設計になっている。1回の寄附に
複数商品が含まれる場合(例: 呉本様の3商品)も同様に**別々の送り状に分割する**
(ユーザー確定・「別々の送り状にしましょう」)。

複数item(複数行)を持つ注文JSONは、`tools/export_furusato_goq_csv.py`が自動的に
受注番号へ`-1`/`-2`の枝番を振って別々のCSV行に分割する。パーサー側は「合算しない」だけでよい。

**ただしGoQ側では、取込後に自動同梱が同一人物の受注を1受注へ統合する**(2026-09-28に5人・
2026-10-06に11人で確認)。統合先は枝番の最後の受注で、統合された受注は一覧から消え、内容品は
全行が統合先にまとまる(数量も一致)。つまり「別々の送り状」ではなく**1受注=1個口**になる。
このため取込後の照合は枝番トークンでは見つからない(`goq_lookup` は「見つかりません」になる)。
氏名とoid範囲で照合し、`sent/*.json` の `result.oid` は**残った受注のoid**にして
`note` に「統合」と書く(`export_shiftplus_shipped_csv.py` がこのnoteで統合先を照会する)。
`tools/finalize_furusato_registered.py` がこの照合と記録を行う(下の4)。
ネコポスの同梱(あられ2〜3個)は1個口に入るかを発送時に確認する。

**同一商品コードが1つの注文JSON内に複数あってもエラーにしない**(2026-09-07、高橋様の
実例で発覚。有本様と同型)。`order_model.validate_order()`の「codeが重複しています」は
本来register_only(047が1受注内の重複コード行を拒否する)向けのチェックで、export時に
必ず分割されるこのチャネルには当てはまらない。`furusato_shiftplus_csv.py`はこのエラー
文言だけを結果から除外してから検証エラー判定する。

## 3. あられの商品名は短縮する(送り状の内容品欄が切り詰められるため)

GoQの送り状「内容品」欄は商品名の先頭を一定文字数で切り詰めて印字する(2026-09-02実測)。
元の商品名(「【1,000円寄附】水兵あられ(しょうゆ) ku091-067-r」)だと**フレーバーの
判別情報が切れて消える**。`furusato_shiftplus_csv.py`の`ARARE_SHORT_NAME`が既知の
あられ3コードを短縮名に変換する:

```python
ARARE_SHORT_NAME = {
    "ku091-067-r": "水兵あられ(しょうゆ)",
    "ku091-068-r": "水兵あられ(味このみ)",
    "ku091-069-r": "水兵あられ(海老つまみ)",
}
```

新しい返礼品コードが増えた場合、その商品名も長い/紛らわしいなら同様の短縮を検討する。

### あられの配送会社閾値(合算はしないが、1受注内の数量には適用する)

同一寄附(1つの寄附受付No)のあられが**4個まではヤマト運輸のネコポス1通。5個以上は4個ずつに分割した
複数の受注にする**(5個→4+1、6個→4+2、10個→4+4+2。各受注がネコポス・受注番号 `<寄附受付No>-P1`,`-P2`…)。
**佐川急便・宅急便には切り替えない**(2026-10-07 ユーザー決定。それまでは5個以上が佐川急便。同日午前に一度
「ヤマトの宅急便」に決めたが、4個ずつ分割に取り消した)。既に登録済みの江本様(6個・oid 113930・佐川)は
**変更しない**(次回から)。
(`ARARE_YUPACKET_MAX_QTY = 4`・`apply_arare_rule` が分割・`ARARE_CARRIER`/`ARARE_SHIPPING_KIND`。2026-10-02に
クリックポスト値上げを受けてゆうパケ→ネコポスへ変更。2026-09-14以前はクリックポストだった。
あられ以外の商品は従来どおり日本郵便のゆうパケ。CSV取込でヤマト運輸/ネコポスが受理されることは
2026-10-06の先行3件で確認済み。047の送り状発行は2026-10-02にヤマト検出バグを修正済み)。ただし上記の「合算しない」ルールにより、通常は
1受注=1商品=数量1なので、この閾値に達することは稀(同一寄附で同じあられを5個以上
選んだ場合のみ発動)。

## 4. GoQへ登録する(カスタムCSV取込・10件超は必須)

```bash
python tools/export_furusato_goq_csv.py       # orders/FURUSATOCSV-*.json → 取込用CSV生成
python tools/export_furusato_goq_csv.py --out reports/GoQCSV_ふるさと_YYYYMMDD_test3.csv orders/FURUSATOCSV-A.json orders/FURUSATOCSV-B.json orders/FURUSATOCSV-C.json   # 先行3件
```

**実行の順(2026-10-06の手順)**:

1. 一覧をアーティファクトで出して承認を得る(件数・配送別・要確認の黄色行)
2. **先行3件**(あられ3種を1件ずつ)を取り込み、`fetch_goq_info` で配送(ヤマト/ネコポス等)・宛先・
   「新規受付」を読み直して確かめる
3. 問題なければ**残りを取り込み**(`export_furusato_goq_csv.py` に残りのファイルを明示して別CSVで)
4. 取込はPython3.12(Playwright入り)で `047.GoQ送り状再印刷/goq/_run_csv_import.py <CSV>` を実行
   (`C:\Users\user\AppData\Local\Programs\Python\Python312\python.exe`。送信→確認画面→実行まで1回で行う。
   **実行後にURLが変わらないことがあるが、再実行しない**(二重登録になる)。まずGoQを読み直す)
5. 照合と記録: `python tools/finalize_furusato_registered.py --first-oid <先頭oid> --last-oid <末尾oid> --csv-label <CSV名>`
   (確認だけ。問題0件で `--apply` を付けると `orders/` → `sent/` へ移す)。oid範囲は先行3件の
   oidから推定し、**取込直後の連番**であることを確かめる
6. 統合された受注の内容品がGoQで一致しているかも見る(氏名で一覧を検索して品名×数量を数える)

- 出力は**商品名でソート済み**(ピッキング時に同じ商品をまとめて処理できるように)
- **列名はGoQの正式名称と1文字でも違うと自動マッピングされず無言でスキップされる**
  (`個数`・`お支払い方法`・`注文者氏名（カナ）`全角括弧・`注文者住所：都道府県`等、
  6列で実際に食い違いが発生した)。`export_furusato_goq_csv.py`のHEADER定数を変更した場合は
  必ずアップロード後の列マッピング確認画面で全列を目視確認する
- 手順: GoQ(`https://order.goqsystem.com/goq21/modules/CustomImportCSV/index.php/top/`)で
  対象店舗(唯一の選択肢「CSV」)を選ぶ→CSVファイル選択→「送信」→「確認して実行」
  (列マッピング確認画面が出る、**ここでユーザーに確認を取る**)→「実行」
- 実行後、URLが変わらないことがある(AJAX的処理)。**必ずGoQを読み直して照合する**
  (`tools/goq_lookup.py`の`fetch_goq_info`)。20件超でも1回のバッチ照会で足りる
- アップロード前のCSV内容は、件数が多い場合ほどアーティファクト(HTMLテーブル)で
  一覧表示してからユーザー確認を取る

登録後の`orders/*.json` → `sent/` への移動と `result` へのoid記録は
`tools/finalize_furusato_registered.py`(上の5)で行う。手でJSONを書き換えない。

## 4.5 送り状の住所エラー(ヤマトB2クラウド WS001002)の直し方

エラーレポートの形: `配送管理番号 113884-1 / WS001002 / consignee_address2 /
お届け先郵便番号とお届け先市区郡町村が一致しません`。配送管理番号の先頭の数字がGoQ管理番号(oid)。

- **原因**: 住所1の「市」と「区」(「郡」と「町村」)の間に空白が入っている(例「川崎市 麻生区…」
  「大里郡 寄居町…」)。2026-10-06の取込で3件発生。以後は `join_address` が空白を入れない
- **直す**(ユーザーが依頼した受注だけ。書き込みなので1件ずつ現在値を確認してから):
  GoQの注文内容修正ページ(`order_derivery2_1_4.php?oid=<oid>`)の「住所1」から空白を取り、
  「この内容で保存する」。ツール化済み:
  ```bash
  # Python3.12(Playwright入り)で。--expect が今の値と一致しないときは何も書かない
  python 047.GoQ送り状再印刷/goq/set_addr1.py <oid> --expect "川崎市 麻生区栗平二丁目4番25" --new "川崎市麻生区栗平二丁目4番25"
  ```
  変更前の配送先を `047.GoQ送り状再印刷/probe_out/` へ退避し、保存後に開き直して**変わった欄**を表示する
  (住所1だけが変わっていること)
- 直したら**ユーザーが送り状を再発行**する(送り状の発行はこちらでしない)
- 同じ取込の他の受注に同じ形(住所1が市/郡で終わり住所2が区/町村で始まる)が無いかも探す
  (`sent/*.json` の `ship_to.addr1` / `addr2` を走査)

## 5. 誤登録の訂正(GoQは物理削除できない・キャンセルのみ)

商品名を間違えた等でGoQ側を修正したい場合:

1. GoQ側で該当受注を**キャンセル**(削除機能は無い。ユーザーが手動で行う)
2. **同じ受注番号は再利用しない**。元の受注番号に`-2`枝番を付けて新規登録する
   (例: `FURUSATOCSV-34202260003669` → `FURUSATOCSV-34202260003669-2`)
3. 元の`sent/*.json`は`status: "superseded_canceled_in_goq"`にして残す(履歴として)
4. 新しい`-2`版を`orders/`に作り、通常の登録フロー(手順4)で再登録する

## 6. シフトプラスへ出荷完了を通知する(専用CSVアップロード)

出荷処理(送り状発行)が終わったら、GoQとは別に**シフトプラス側にもCSVアップロードで
出荷完了を知らせる**必要がある。

```bash
python tools/export_shiftplus_shipped_csv.py            # 未通知分のみ・CSV出力+マーク
python tools/export_shiftplus_shipped_csv.py --all       # 全件・マークしない(確認用)
```

列は`配送No/伝票番号/配送業者/出荷予定日`(CP932)。

**🔴 最重要の罠(2026-09-02、実際にアップロード事故が発生)**: **「配送No」列は
シフトプラス側の「配送No.」の値**(例`20260005112`)であり、**GoQの受注番号ではない**。
最初の実装ではGoQ受注番号を入れてしまい、シフトプラス側のアップロードで受理されなかった。
正しくは、出荷依頼CSVの各行が持つ「配送No.」列を`furusato_shiftplus_csv.py`が
item単位で`delivery_no`として保持しており(パース時に`row.get("配送No.")`から採取)、
`export_shiftplus_shipped_csv.py`はこの`delivery_no`をそのまま1列目に出す。
GoQ受注番号は**GoQへ照会して伝票番号・配送会社を読み取るためだけに使う**(出力しない)。

- 伝票番号・配送業者は実際に出荷処理した後にGoQから読み取った実データ
  (`goq_lookup`経由・register_only時点の予定値ではない)
- 出荷予定日 = **実行日**(YYYY/MM/DD)
- 送り状未発行(GoQのtracking_noが空)の注文は自動的に対象外
- 既定は「未通知分のみ」(`sent/*.json`の`shiftplus_reported_at`で管理、Sankeiの
  `make_sankei_report.py`と同じパターン)
- **アップロード前に実物サンプルと突き合わせて検証すること**(2026-09-02、ユーザーの
  既存VBAツールがGoQから直接抽出したサンプルと「配送No/伝票番号/配送業者/行順」が
  完全一致することを確認済み)

### 6.5 送り状番号を GoQ の外で発行した場合(クリックポスト等)の入力 — 2026-10-04

クリックポストの送り状をGoQのAPIでなく別の画面(クリックポスト等)で発行すると、GoQの受注は
「作業中5」のまま伝票番号が空になる。ユーザーから「氏名と番号の一覧」を受け取ったら、**GoQの伝票取込**
(`001.Python/103.GoQ出荷処理サポート/upload_to_goq_fuji_auto.py`・制服のフジ用)で入れる。

1. 氏名→GoQ管理番号(oid)の対応を作る(`sent/*.json` の `result.oid` と、GoQの宛名を `fetch_goq_info` で
   突き合わせる)。**全員が1対1で、番号が12桁・重複なし**を確かめ、アーティファクトで一覧を出して承認を得る
2. CSV(CP932・列 `GoQ管理番号,お荷物伝票番号,出荷日,配送業者,ひとことメモ`)を作る。
   **ひとことメモは空欄**(GoQのメモは追記式で取り消せない)・配送業者は「日本郵便」・
   出荷日はユーザーに聞く(CSVの日付でGoQの出荷日が上書きされる)
3. `python upload_to_goq_fuji_auto.py --check-only --headless --csv-path <CSV>`(ログインとアカウント確認だけ。
   CSVは**更新から300秒以内**でないと拒否されるので直前に `touch`)→ **1件だけ**取り込み → `fetch_goq_info` で
   伝票番号が入り、ステータス・配送が変わっていないことを確認 → 残りを取り込む
4. 全件を読み直して、伝票番号の一致・ステータス不変・配送不変を確認する
5. その後に「6. シフトプラスへ出荷完了を通知する」を行う

## 7. GoQのステータス文言だけで出荷済みと判断しない

GoQの受注ステータスが「処理済」でも、送り状番号(伝票番号)が一切記録されていない
(＝実際には未出荷)ケースが実際に発生した(2026-09-02、SANKEI-319109/319280で発覚。
産経チャネルの実例だが同じ罠がこのチャネルにも当てはまる)。**必ずtracking_noの有無で
「本当に出荷済みか」を判定し、ステータス文言だけでは判断しない**。
