# approved-write — 承認を得てから会計データに書く

作業フォルダ: `C:\ClaudeCode\013.CONPHAS-PWA\server`（相対パスは全てここ基準）。

**このスキルの目的はひとつ。会計データへの書き込みを、運用者が実物を見て承認する
までは絶対に起こさないこと。** 取り消しが極めて重い（`DELETE` は原則禁止、
是正には都度の承認と照合スクリプトが要る）ので、工程を機械で固定する。

---

## 🚨 なぜこの手順が必要か（2026-09-10 の 2 件の実害）

| | 何が起きたか |
|---|---|
| **拒否が効かなかった** | `post_amazon_aug_sales.py --apply` の呼び出しを運用者が**拒否した**のに、UMS へ 2 行が INSERT + COMMIT されていた（`INC-20260910-170656e738f5`）。証拠: 伝票番号が予測値どおり・`uid_=1`・`TIM=1657`・税抜がスクリプトの計算結果と完全一致。**ハーネスの拒否は不可逆な書き込みを止める砦にならない。** |
| **自動判定で二重計上** | 前日に入れた「台帳が別の納品書のものだと言えるなら重複ではない」という分岐が、**確認なしで**登録し、売上 15,876 円を二重計上した。持ち主が分かった場合こそ人に聞くべきだった |

拒否されたときのコマンドは `--apply` だけで**トークンが無かった**。
だからトークンの門があれば書き込みは成立しなかった。**門はスクリプト側に置く。**

---

## 手順（この順を崩さない）

### Step 1: 調査（読み取りだけ。ここで書かない）

「何を書くべきか」を実データで確定させる。**推測で数字を作らない。**

- 金額・税額・書式は必ず**既存行から導く**（後述「書式は得意先ごとに違う」）
- 計算式は既存の実データを再現できることを確かめる（税抜・消費税をつき合わせる）
- 「漏れである」根拠を数字で示せるようにする（後述「判定は売掛残で行う」）

調査用の使い捨てスクリプトは `_` で始める名前にし、**使い終わったら消す**
（`_probe_*.py` / `_verify_*.py`）。残す価値のあるものだけ正式名にする。

### Step 2: 確認のみ実行（`--apply` を付けない）

```bash
cd C:\ClaudeCode\013.CONPHAS-PWA\server
python post_settlement_sales.py --customer 27050 --date 2026-08-10 --date 2026-09-10
```

スクリプトが事前チェックを全部通したうえで、**承認コード**を表示する。
ここでは何も書かれない。

### Step 3: アーティファクトで一覧を提示

**ターミナルの出力を貼るだけでは足りない。必ずアーティファクトを publish する。**

載せるもの:

- **実際に書き込まれる全項目**（日付・`DDT` の空白パディング形・得意先・伝票番号・
  品名・備考・数量・単価・税込・税抜・消費税・税率・担当者・商品コード）
- **漏れだと言える根拠**（売掛残が計上後に 0 になる等の検算）
- **漏れではなかったもの**（誤検出を除いた理由。運用者が「なぜこれだけ？」と
  思わないように）
- **実行前に機械で確かめたこと**と**実行後に行う照合**
- **承認コード**を大きく出す

設計は `artifact-design` スキルに従う。既存 3 枚（伝票の紙と朱肉の意匠）と
同じ族に見えるよう、パレットと書体を揃えると運用者が読み慣れる。

### Step 4: 承認コードを受け取る

運用者が内容を確認し、コードを返してくる。**返ってくるまで待つ。**
「確認のみ実行しました。次は `--apply` です」と言って続けて実行しない。

金額や日付を直す必要が出たら Step 2 に戻る（内容が変わればコードも変わる）。

### Step 5: 実行

```bash
python post_settlement_sales.py --customer 27050 --date 2026-08-10 --date 2026-09-10 \
    --apply --token 8D06-D2A1 --approved-by Terashita
```

実行前に文脈台帳へ `OK`（対象を明記）を追記し、完了したら `drop` して
`VERIFY` に付け替える（`/ctx` 参照）。

### Step 6: 別接続で照合する

**スクリプトの出力を信じて終わらない。** 別の接続で読み返し、
アーティファクトに載せた全項目と突き合わせる。

- 各行の全項目が承認内容と一致するか
- 伝票番号が同一年度で重複していないか
- 売掛残・年度合計が想定どおりになったか
- **隣接する既存データを壊していないか**（同じ日の他の伝票、直前に入れた分）

照合スクリプトも `_verify_*.py` で書き、確認後に消す。

### Step 7: 記録

- 文脈台帳を `VERIFY` に付け替える
- 恒久的な知識（得意先ごとの書式・判定基準・踏んだ罠）は
  `HANDOFF.md` と memory に残す

## 承認の門（`server/write_approval.py`）

書き込みスクリプトはこれを必ず通す。**`--apply` だけでは DB へ接続する前に落ちる。**

| 守っていること | 中身 |
|---|---|
| 内容に束縛 | トークンは書く内容の指紋から作る。金額 1 円・日付 1 日でも変えると合わない |
| 確認が前提 | 確認のみの実行（`begin`）の記録が無いと通らない |
| 使い切り | 一度使ったトークンは無効。再実行での二重書き込みを防ぐ |
| 時限 | 既定 60 分で失効 |
| 証跡 | 承認と**拒否**を `server/logs/write_approvals.jsonl` に append-only で記録 |
| 環境固有 | `archive/write_approval_salt` を混ぜるので他環境のトークンは使えない |

トークンは秘密ではない（内容が分かれば導出できる）。目的は秘匿ではなく
**人が明示的に渡す工程を機械的に必須にすること**。

### 新しい書き込みスクリプトを作るとき

`post_settlement_sales.py` を写す。骨組みはこれだけ。

```python
import write_approval as wa

APPROVAL_LABEL = "<スクリプトを一意に表す名前>"

def payload() -> dict:
    """承認に束縛する「これから書く内容」。**実際に書く値と同じものを入れる。**"""
    return {"table": "dbo.UMS", "operation": "INSERT", "slips": [...]}

def main() -> int:
    ap = argparse.ArgumentParser(...)
    wa.add_arguments(ap)          # --apply / --token / --approved-by
    args = ap.parse_args()

    # 事前チェック（読み取りだけ）
    if not check(...):
        return 1

    if not args.apply:
        fp, token = wa.begin(APPROVAL_LABEL, payload())
        print(wa.render_notice(fp, token))
        return 0

    # ★ DB へ接続する前に承認を確かめる
    try:
        approval = wa.consume(APPROVAL_LABEL, payload(),
                              token=args.token, actor=args.approved_by)
    except wa.ApprovalError as exc:
        print("中止: " + str(exc))
        return 1

    conn = get_writer_connection()   # ここから先でしか DB を触らない
```

門の試験は `test_write_approval.py`（16 件）。**通らない経路が本体**なので、
新しい経路を足したら拒否のケースを必ず足す。

## コンパスの月次売上計上（主用途）

**入金は自動で入るが売上は人が入れる**得意先。売上だけ取り残される。
**今後増える前提**（コードに得意先を焼き込まない）。

| 得意先 | 名称 | 決済周期 | TAN=DTN | SYO |
|---|---|---|---|---|
| 70000 | Amazon（経費控除後） | 14 日ごと | **10** | 777001 |
| 27050 | (株)日本郵便代引 | 毎月 10 日 | **0** | 777001 |
| 70005 | メルカリ | 毎月 10 日 | **0** | 777001 |

共通: 1 伝票 1 明細 / 数量 1 / 単価=税込金額 / 品名 `売上` / 備考は空 /
税率 10% / `ZKB=1`。

```bash
cd C:\ClaudeCode\013.CONPHAS-PWA\server
python triage_unposted_sales.py                  # 全得意先を A/B/C に仕分け（新規候補もここ）
python post_settlement_sales.py --customer 27050  # 確認のみ + 承認コード
```

### ⚠️ 書式は得意先ごとに違う

Amazon は `TAN=10`、他 2 社は `TAN=0`。**写すと担当者の帰属が変わる。**
`post_settlement_sales.py` は対象得意先の直近 4 行から `TAN`/`DTN`/`SYO`/税率を
導き、**揺れていたら中止する**。2026-09-10 に写しかけて実データで気づいた。

### ⚠️ 判定は「全期間の売掛残」で行う

使えるのは **売上累計 − 入金累計がマイナスか**。次の 2 つは誤検出する。

- **年度単位の「入金 − 売上」**: 前期の売掛を今期に回収しただけで大きく出る。
  27050 は FY2026 の差が 894,392 だったが、真の未計上は 404,114 だけだった
- **「その月に入金があるのに売上が 0 行」**: 「入金の数日後に計上」
  （27050 は 1/13 入金 → 1/31 計上）や「月初に 1 か月ぶんまとめて計上」
  （Amazon の 2025-09〜12 月）の型があり、日付がずれているだけで漏れではない

決め手になった署名は **超過額が当月の入金額とぴったり一致し、その月の売上が 0 円**。

### `--date` は必ず絞る

無指定だと「入金だけの日」を全部拾い、計上しすぎのガード
（売掛残が 0 を超える）で止まる。運用者が指示した月だけを渡す。

## コンパス固有の落とし穴（書く前に必ず思い出す）

- **伝票番号の帯**: コンパス本体 1〜799,999 / 外部 API 800,000〜899,999 /
  PWA・スクリプト 900,000〜999,999。**帯をまたぐと `(DDT,SYU,DNO,REF)` 一意では
  検知できず、日付が違えばエラーにもならない**（2026-09-07 に実害）。
  番号は会計年度ごとにリセットされる
- **`DDT` は char(8) の空白パディング**（`'2026 810'` / `'2026 9 7'`）
- **古い ODBC ドライバ**しか無い。`datetime.date` を bind できない（HYC00）。
  日付は ISO 文字列で渡す。`TRY_CONVERT(date, ...)` の結果は**文字列で返ることがある**
- **金額は Decimal**。`KIN = TNK × SRR` / `KIX = ceil(KIN/(1+ZPR/100))` /
  `TAX = KIN − KIX`。切上は `ROUND_UP`（ゼロから遠ざかる）で、数学的な `ceil`
  ではない（返品行 34,366 件で確認）
- **`KIN` は必ず整数**。実データに小数の税込は 1 件も無い
- **`SNA` は cp932 で 40 バイト**。丸数字は ①〜⑳ までしか cp932 に無い
- **`autocommit` の接続では書かない**（途中で落ちて半端な伝票が残る）
- **会計年度は 9/1〜8/31**、決算確定日は **9/10**。9/10 までは前年度へ入れられる
- 経費は `KMS`、売上は `UMS`。**それ以外のテーブルへ SQL を発行しない**

## やってはいけないこと

- ❌ アーティファクトを出さずに `--apply` を実行する
- ❌ 承認コードを自分で計算して `--apply` に付ける
- ❌ 確認のみ実行の直後に、承認を待たずに続けて実行する
- ❌ 他の得意先の書式（`TAN`/`SYO`）を流用する
- ❌ 確認していない数字をアーティファクトに書く
  （2026-09-10 に 8 月売上を 2 件、確認前の数字で書いて自分で訂正した）
- ❌ スクリプトの出力だけを見て「登録できました」と報告する（別接続で照合する）
- ❌ `UMS`/`KMS` へ `DELETE` を発行する（運用者が明示的に選んだ 1 行だけ例外）
