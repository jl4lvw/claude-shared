# receipt — 領収書発行

作業フォルダ: `C:\ClaudeCode\091.領収書発行`(コマンドは絶対パスで実行する)。
発行者(株式会社制服のフジ)・角印・紙面は `issuer.json` / `kaku.png` / `receipt_template.html` に固定済み。**紙面は最終デザインで確定済み**(詳細は同フォルダの `DESIGN.md`)。

## 0. 最初にやること(省略禁止)

1. **`C:\ClaudeCode\091.領収書発行\reservations.md` を読む。** 「未発行」に予約があれば、ユーザーの依頼がそれかを確認する(依頼が「領収書発行」だけのときは、予約の一覧を示して「どれを発行するか」を `AskUserQuestion` で聞く)
2. 予約の内容は**予約時点のもの**。発行前に宛名と但し書きを必ず再確認する(下の手順 1)。金額は GoQ で再確認してよい
3. 発行したら、`reservations.md` の該当予約を「発行済み」へ移し、台帳の発行番号を書く
4. 発行予約を新しく頼まれたら、**発行はせず**、`reservations.md` の「未発行」に宛名・金額・但し書き・備考・根拠・発行後にやること(メール返信など)を書く

## 手順

### 1. 入力を揃える
**🔴 宛名と但し書きは、毎回必ず `AskUserQuestion` で確認する(省略禁止・2026-10-14 ユーザー指示)。** GoQ の注文者名・予約の内容・これまでの値をそのまま使わない。
- **宛名**: 「このままでよいか」を聞く。候補は GoQ の注文者名・メールで指定された名称など。**依頼メール(注文者からの要望)に宛名の指定がないかを `/mail-search` で受注番号を検索して先に確認**し、見つけたら根拠(メールの該当箇所)と一緒に示す。個人は様、法人・団体・官公庁は御中
- **但し書き**: **基本は「商品代として」**。相手から指定があれば、その内容を加味して変える。「送料として」「商品代及び送料として」などは**入れない**(送料込みの金額でも「商品代として」)。選択肢は「商品代として(基本)」+ 相手の指定

聞く項目(分かっているものは聞かない): 宛名・敬称・税込金額(10%対象 / 8%対象)・但し書き・備考(任意・最大4行)・発行日(省略=今日)。
- 金額は**税込**。税抜で渡されたら税込に直してよいか確認する(税抜のまま計算しない)
- 宛名40文字・但し書き60文字・備考200文字/4行を超えると受け付けない
- 売上の根拠(GoQ・コンパス)から金額を拾う場合は、元データと突き合わせてから指定する

#### GoQ の受注番号・管理番号から金額を取る場合(読み取り専用)
GoQ に REST API は無く、042 の DB には新しい受注が入っていないことがある(同期が数時間遅れる)。確実なのは GoQ の受注 CSV。
1. 注文日で CSV を取る(個人情報を含むので出力先は scratchpad): `python C:/ClaudeCode/001.Python/118.GoQ過去注文取得/fetch_orders.py --from YYYY-MM-DD --to YYYY-MM-DD -o <scratchpad>/goq.csv`(約1分。注文日が分からなければ範囲を広げる)
2. `python C:/ClaudeCode/091.領収書発行/issue_receipt.py from-goq --csv <scratchpad>/goq.csv --key 20-10034546`(受注番号・GoQ管理番号どちらでも可)
   → 請求金額・商品・送料・注文者名・**備考用の文字列(受注番号を含む)** が JSON で出る。`suggest.amount10` と `suggest.memo` は使える。**`suggest.to`(注文者名)は宛名の候補にすぎない**(上の確認を必ず通す)
- 金額は**請求金額**(値引き後に実際に払う額)。送料を含む。但し書きは基本の「商品代として」のまま(送料の文言は入れない)
- 税率は10%に仮置き。8%(軽減)の商品を含む注文は、商品ごとに分けて `--amount8` を指定する(GoQ の項目だけでは判定できない)
- `bundled: true`(同梱で複数の受注番号が1つの管理番号)は、合計と備考(受注番号をすべて記載)が正しいかをユーザーに確認する
- 備考には**受注番号を必ず入れる**(ユーザー指示)。取得した CSV は個人情報を含むので、用が済んだら scratchpad から消す

### 2. プレビュー(台帳は変わらない)
```
python C:/ClaudeCode/091.領収書発行/issue_receipt.py preview --to "宛名" --amount10 33000 --amount8 0 --for "商品代として" --memo "備考" --out <scratchpad>/receipt_preview.html --page <scratchpad>/receipt_page.html --note "宛名の根拠: ..." --note "金額の出所: ..."
```
最終行の JSON に `no_planned`(予定の発行番号)・`total`・`stamp`(印紙欄の有無)が出る。
**`Artifact` ツールで `receipt_page.html`(承認用ページ。紙面は発行用テンプレートそのもの・左に内容一覧と `--note` の根拠)を公開し、内容(宛名・金額・内訳・番号・印紙欄の有無)を示して承認を得る。** 承認前に `issue` を実行しない(台帳に記録が残り、番号が進むため)。
再発行は `--reissue-of R-20261014-001`(枝番でも可)を付けて同様にプレビューする。

### 3. 承認後に発行
プレビューと同じ引数で `preview` を `issue` に替えて実行する(`--out` `--page` `--note` は不要)。
```
python C:/ClaudeCode/091.領収書発行/issue_receipt.py issue --to "宛名" --amount10 33000 --amount8 0 --for "商品代として" --memo "備考"
python C:/ClaudeCode/091.領収書発行/issue_receipt.py issue --reissue-of R-20261014-001
```
- 内部で「採番 → PDF作成 → 1ページか確認 → 台帳に追記 → NASへコピーして照合」を行う。PDF作成に失敗した場合は台帳に何も残らない
- 失敗は exit 1(stderr に理由)。ロック待ち・1ページに収まらない場合は、内容を直して再実行する

### 4. 結果を確認して報告する(「実行した」で終えない)
最終行の JSON を読み、次を確認してから報告する。
- `nas_ok` が `true`(コピー後の中身を sha256 で照合済み)。`false` / `warning` があれば**そのまま伝え**、PDF はローカルの `issued/` にあることも伝える
- `pdf` のファイルが存在する
- `SendUserFile` で PDF をユーザーへ渡す(`display: "attach"`)
- 報告には発行番号・宛名・税込合計・印紙欄の有無・保存先を書く。印紙欄が出た場合は、紙に印刷して渡すなら印紙の貼付と消印が必要なことを一言添える
- 領収書をメールで送る依頼があるときは `/mail-send`(下書きまで・送信は人が押す)。予約に「発行後にやること」があれば、それも案内する

## 守ること
- **`issue` を動作テスト目的で実行しない**(本物の台帳・NASに記録が残る)。確認は `preview` か `pytest`(`python -m pytest C:/ClaudeCode/091.領収書発行/tests -q`。台帳・NASは一時フォルダに隔離される)で行う
- **発行予約を受けたセッションでは発行しない**。予約は `reservations.md` に書くだけ。実発行は、別の依頼で、手順 1〜3 を通して行う
- 台帳・`issued/` のPDFを手で編集・削除しない。誤発行は、そのまま残して再発行(枝番)か、ユーザーに相談する
- 同じ番号での上書き再発行はしない(別番号の枝番にする方針)
- **紙面は最終デザイン。** 変更はユーザーの明示的な承認を取ってから。`receipt_template.html` / `issuer.json` / `kaku.png` を直し、`preview --page` の承認ページで見た目を見せ、`pytest` を通す。承認ページは `preview --page` で作る(手作業で紙面を組み替えない)
- 角印・発行者情報を外部サービス(外部AI・外部API)へ送らない
