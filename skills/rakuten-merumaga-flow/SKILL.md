# /rakuten-merumaga-flow — 検査 → 原稿 → 下書き登録（ラッパー）

メルマガ作業を、次の順に 1 本で進める。**各段階が通ったときだけ、次へ進む。**

```
① 原稿の取得（/rakuten-merumaga 手順 1〜3）   メルマガエディタ → 貼り付け用タグ → ローカル保存
② 内容のチェック（手順 6）                    リンク切れ・説明違い・欠品 …… エラーなら終了／警告はユーザーに選ばせる
③ 原稿作り                                    HTML 原稿・テキスト版・携帯用テキスト（5,000 文字以内）
④ 下書き登録の申請                            端末 A の RMS 下書き登録へ申請（A が RMS に「下書き」を保存）
⑤ 結果の確認                                  下書き ID・照合結果を報告し、運用者に RMS での配信予約を頼む
⑥ 予約受付メールの確認                        「【RMS】R-Mail 配信予約を受け付けました」が下書きの ID 分そろうまで待つ
⑦ LINE で完了を知らせる                       承認の画面で承認 → 「楽天メルマガ配信」グループへ送る …… ここまででスキルの完了
```

**完了の条件（2026-10-24 運用者決定）**: 下書きができた時点では終わりではない。運用者が RMS で配信予約し、
予約受付メールを下書きの ID ごとに確かめ、LINE で完了を知らせたところで、このスキルは完了。

呼び出し側のスキル（それぞれ単独でも使える）:
- `/rakuten-merumaga` … ①②③の部品（`C:\ClaudeCode\.claude\skills\rakuten-merumaga\`）
- 端末 A の RMS 下書き登録 … ④（A の `rakuten_login\mail_draft\`。README 参照）

## 🚨 絶対ルール

1. **配信・配信予約・送信・配信日時の設定は、しない。** Claude が作るのは下書きまで。配信日時・対象の設定と配信予約は、運用者が RMS で行う（Claude はその完了をメールで確かめて知らせるだけ）。下書きの保存時に運用者宛のテストメールが 1 通届くのは道具の仕様（宛先 mm@seifukunofuji.com・2026-10-24〜。`rakuten_login/config.py` の `TEST_MAIL_ADDRESS`）。
2. **RMS の画面操作は、端末 A だけで行う**（ブラウザは A の `rakuten_login` の専用プロファイル 1 つに固定）。TK では RMS にログインしない・パスワードの入力や貼り付けをしない。
3. **メルマガ（テンプレート）の修正はしない。** 検査の指摘は、報告して終わる（修正は別担当者の仕事）。
4. **リンク検査のエラー（載っている商品がすべて販売不可）は必ず止める。** 警告は、内容を見せて、ユーザーに「続行／中止」を選ばせる。
5. **携帯用テキストが 5,000 文字を超えたら、勝手に削らず止める**（RMS の画面の制限と同じ。超過量と削る候補を報告）。
6. **失敗した申請は、自動で再申請しない。** 原因を報告して、ユーザーに聞く。
7. 質問は最初にまとめて聞く（下の「最初の質問」）。席を外されても止まらないように、途中の質問は「警告の続行確認」だけにする（承認の画面での承認・運用者の配信予約は「待つ」もので、質問ではない）。
8. **LINE の完了の知らせは、予約受付メールを下書きの ID ごとに確かめてから**送る。運用者の「予約しました」の一言だけで送らない。

## 最初の質問（ブラウザ操作より前・ログイン後の一覧が出た時点で 1 回だけ）

1. **メルマガエディタに入って、候補（更新が 5 日以内）を取得する**（`/rakuten-merumaga` の手順 1〜2。ここまでは質問なしで進める）。0 件なら「5 日以内の更新はありません」と報告して終了。
2. **AskUserQuestion で、次を 1 回にまとめて聞く**（候補の取得後にしか分からないので、ここで聞く）:
   - どのテンプレートか（候補の名前と更新日時。1 件でも確認する）
   - **HTML メールの件名**（担当者が LINE「楽天メルマガ配信」で指示した文字列。呼び出し時に「件名: …」と書かれていれば、聞かない）
     - 「LINE の履歴を読んで判断して」と言われたら、090 の受信記録を**読み取り専用**で開き、そのグループの直近の依頼から件名を取る（`090.LINE業務指示エージェント/data/line_agent.db` の `line_messages`。`target` はグループ ID（会話に書かない）、`received_at` はミリ秒）。依頼の時刻とテンプレートの更新日時が近いものを選び、どの発言から取ったかを 1 行で宣言する（2026-10-24 実例: 13:24 の「タイトルは…でお願いします」）
3. 回答後は、**警告の続行確認以外では止まらず**に、④の申請の送信まで進める。

## 手順

### ① 原稿の取得
`/rakuten-merumaga` の手順 3 のとおり（編集 → 次へ → 「貼付用タグをコピー」→「タグをコピーする」→ `save_clipboard_tag.py --expect <画面の文字数>`）。保存先 `C:\ClaudeCode\900.ClaudeCode\000.tmp\merumaga_tag_YYYYMMDD_HHMM.txt`。
- ⚠ エディタを開くと、テンプレートの「更新日時」が変わる（内容は変わらない）。タグの取得に必要な 1 回だけ開く。
- 編集画面は、最後に必ず一覧へ戻る（保存しない）。
- **絵文字があると `--expect` が合わない**: 画面の「文字数」は絵文字を 4、保存スクリプトは 1 と数える（例: 「👀」1 つで 3 ずれる）。クリップボードの中身で Shift_JIS に無い文字を確かめ、その分を引いた数で保存する（中身は変えない）。
- **絵文字は RMS で「?」に化ける**（2026-10-24 実機: 携帯用の照合で「CHECK👀」→「CHECK?」）。見つけたら②の報告に「絵文字 N 個（RMS で ? になる）」と書き、担当者が直すか決める。

### ② 内容のチェック
```
python ".claude/skills/rakuten-merumaga/scripts/check_mail_links.py" "<タグ.txt>" --json "000.tmp/check_<日時>.json"
```
| 終了コード | 意味 | 動き |
|---|---|---|
| 2 | エラー（全商品が販売不可） | **止める**。理由を報告して終了 |
| 1 | 警告あり | 警告を一覧にして見せ、AskUserQuestion で「続行／中止」を選ばせる（欠品・リンク切れ・説明違い・0 件検索など） |

### ③ 原稿作り + ④ 申請 JSON の作成
```
python ".claude/skills/rakuten-merumaga-flow/scripts/build_draft_request.py" --tag "<タグ.txt>" --subject "<HTML メールの件名>" --template-name "<テンプレート名>" --purpose "<目的>" --out "000.tmp/draft_request_<日時>.json"
```
- 目的の例: `--purpose "10/22 配信の楽天メルマガ(秋の新作 T シャツ)を RMS の下書きに登録し、配信の準備をするため"`
- **purpose(目的)は必須。何のための操作か(誰に何を知らせる・何を補充する等)を 6〜120 字で書く。承認の画面・LINE WORKS・電話の音声案内で運用者に示す。電話の文は外部の音声サービス(Microsoft)へ送るので、人名・住所・電話番号・メールアドレス・お客様名は書かない**（2026-10-21 運用者決定。申請 JSON の `"purpose"` に入る。無い・短い・長いと終了コード 2 で保存しない。A の enqueue でも同じ検査をする）
- HTML 原稿＝貼り付け用タグそのもの。**テキスト版（`html.text_body`）と携帯用テキスト（`mobile_text.body`）は、同じ変換**（`html_to_mobile_text.py`）で作る（HTML メールは RMS で「テキスト部分の本文」が必須のため）。
- 検査（違反は終了コード 2・保存しない）: HTML 100 KB 以下／件名 255 バイト以下（半角換算）／携帯用テキスト **5,000 文字以内**（改行を 2 文字と数えた値）。
- 携帯用テキストが超過したら、止めて報告（超過量・URL が占める分・商品点数）。削り方は、ユーザーに相談する。
- モバイルの件名は A が固定値（『【制服のフジ楽天市場店通信】』）を持つ。申請では指定しない。
- 携帯用テキストとテキスト版は、**Downloads と NAS の両方**にも置く（テキスト成果物のルール。ファイル名 `merumaga_mobile_YYYYMMDD.txt`）。

### ④ 申請を出す

**端末 A で作業しているとき（★）**: relay を使わず、その場でキューへ入れる。申請 JSON の `"source"` は `"A"` にする（TK から来た申請と区別し、同じ内容の再申請が冪等キーで既存の申請に吸い込まれないようにする）。
```
cd C:\ClaudeCode\900.ClaudeCode\rakuten_login
python -m mail_draft.cli enqueue "..\000.tmp\draft_request_<日時>.json"
```
- あとは見張り役が承認の画面へ承認を求め、承認されると実行する。結果は `python -m mail_draft.cli show <id>` が `done` / `failed` / `needs_human` になるまで、裏で待つ（30 秒間隔のループを `run_in_background`）。
- **出し直すとき**: 同じ JSON は既存の申請（失敗のまま）を返すだけ。種類を絞る（`--kinds mobile_text` など。できた方を入れると二重になる）か、`source` を変えて新しい申請にする。

**TK で作業しているとき**: A へ relay で送る。
```
python ".claude/skills/relay/scripts/relay_client.py" send --to A --type task --reserve --file "000.tmp/draft_request_<日時>.json" "【TK→A RMS下書き申請】<テンプレート名>。添付の JSON を enqueue してください(HTML+モバイルテキストの下書き)。配信・予約・送信は不要。実行は運用者が立ち会えるときで可。"
```
- `--to A`（A=本人端末。RC は長張さん端末で別）。送信後は、**スレッドの予約を必ず解放**（`release`）するか、待つなら `wait` で受け取る。
- A は「enqueue → 運用者が立ち会えるときに run → 結果を relay で返信」。**すぐには返らない**ことがある。

### ⑤ 結果の確認
- A の返信（`status` = queued / running / done / failed / needs_human、種別ごとの `rmail_id`・件名・文字数・`match`（開き直しの照合）・スクリーンショット）を表にして報告する。
- `done` かつ `match` が両方「一致」なら、「下書きができました（ID …）。RMS（R-Mail の『送信一覧』）で配信日時・対象を設定して、配信予約をしてください」と伝え、**⑥へ進む**（ここで終わらない）。
- `failed`／`needs_human`／`already_exists` は、画面の文言をそのまま報告して止まる（自動で再申請しない）。ただし `failed` でも、スクリーンショットの送信一覧に下書きができていることがある（照合だけの失敗）。ID を読み取って報告する。
  - `needs_human`「前回のログイン試行から 3 分以内」: 3 分おいて出し直せば通る（ユーザーに聞いてから）。
- 受け取った relay メッセージは `done <id>` で処理済みにする。

### ⑥ 予約受付メールの確認（運用者の配信予約を待つ）
運用者が RMS で配信予約すると、楽天（support@rakuten.co.jp）から「【RMS】R-Mail 配信予約を受け付けました」が **予約 1 件ごとに 1 通**、fw-shopmaster@ の受信箱へ届く。本文の `rmail_id` を下書きの ID と照らし合わせ、**全部の種類の分がそろったら予約完了**。
```
python ".claude/skills/rakuten-merumaga-flow/scripts/reserve_notice.py" wait --ids <HTML の ID>,<携帯の ID> --out "900.ClaudeCode/000.tmp/reserve_<日付>" --timeout-min 360 --check "900.ClaudeCode/000.tmp/check_<日時>.json" [--accept <確かめて問題なしとした警告の URL> ...]
```
- `run_in_background` で回し、運用者には「予約したら自動で気づきます」と伝えて待つ（「予約したら教えて」とは頼まない）。先に `check` で 1 回見る（予約が先に済んでいることがある）。
- 終了コード 0=そろった（`reserve.json`・`body.txt`（LINE の本文）・`spec.json`（画像の仕様）を保存）／13=時間切れ（運用者に予約の状況を聞く）。
- メールの本文は `walk()` で取り出す（古い形式の Message には `get_body` が無い。2026-10-24 にこれで予約メールを見落とした）。
- 配信予約日時が依頼の希望（例「本日 20 時配信希望」）と違っても、運用者が決めたことなので直さない。報告には並べて書く。
- 予約受付メールは「予約を受け付けた」知らせだけ。あとでキャンセルされても分からない。

### ⑦ LINE で完了を知らせる（`/line-notify` の手順 2〜4）
**本文は短く、詳細は画像に書く**（2026-10-24 運用者決定。画像は 5 案から**案 1（確認した観点の表）+ 案 2（リンクごとの表）**を採用）。
本文は `reserve_notice.py` の `body.txt`。URL は書かない（`--url` が末尾に足す）:
```
◆楽天メルマガ 配信予約完了
10/24(土) 15:00 配信(PC用・携帯用)
リンク・在庫を確認しました。
詳しくは画像をご確認ください。
```
画像（`spec.json`）は 2 つの表:
1. **確認した観点**（観点｜結果）… PC 用・携帯用の配信予約（日時・人数）／件名／商品リンクが正しい（n 点）／品切れでない（n 点）／そのほかのリンクが開ける（m 本）。OK は緑、要確認は赤い行
2. **リンクごとの確認**（No｜リンク｜リンク先（G番号）｜在庫｜結果）… 商品は 1 行ずつ、問題のあったリンクも 1 行ずつ、OK のそのほかのリンクは「そのほかのリンク N 本」の 1 行にまとめる（1 枚に収めるため 14 行まで）
- ②の検査結果を `--check` で渡す（渡さないと①の表だけ）。人が確かめて問題なしとした警告（案内文と名前が合わないだけ等）は `--accept <URL>` で「OK(確認済)」にする。**確かめていない警告に `--accept` を付けない**。
- 絵文字は画像の字体に無いので、名前から自動で外す。
- 種類ごとに配信時刻が違うときは、本文に種類ごとの時刻を並べる。
- 画像は `spec.json` から `make_status_image.py` で作る → `line_notify.py publish` → `request-approval --group 楽天メルマガ配信 --purpose "<日付>の楽天メルマガの配信予約が済んだことを担当者に知らせるため"` → `wait-approval`（裏で）→ 承認後に `send --send`。
- 19:00〜翌 9:00 は道具がキューに積む（終了コード 20）。その場合も「翌朝 9:00 に送ります」と書いてスキルは完了扱い。
- 送ったら、LINE のメッセージ ID と、予約内容（種類・日時・人数）を報告して完了。
