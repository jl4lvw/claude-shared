# register-product — 新商品登録(楽天登録済み → 023 / Eストア / Yahoo! / GoQ / 在庫)

G2225(ワッペン)の実登録(2026-09-25)で確立した手順を `pipeline.py` に落としたもの。cgd Lv3
(Codex+DeepSeek の技術×批評4レビュー)で設計を点検し、指摘を反映済み。

**Claude がやるのは「最初にまとめて質問 → 確認画面で承認 → 承認の記録 → パイプライン起動 → 結果報告」だけ。**

対象外(登録しない。完了報告で「未実施」と明記する): Amazon(`/amz-register`)・LCL・7S(コマースロボ)。
スキルの中から別スキルを呼ばない(スキル連鎖禁止)。

## 在庫数は必ず 0 で登録する(絶対ルール・2026-09-28 ユーザー決定)

**在庫数は質問せず、常に 0 として登録する。例外は無い。** 在庫0だと購入できないため、これ自体が
フェイルセーフとして機能する(初回のバリエーション登録やGoQ行対応待ちで途中停止しても、誤った内容で
売れてしまう事故を防ぐ側に倒れる、という業務判断)。実際の在庫数の反映は本スキルの範囲外とし、
別途 `/goq-stock-set` 等で行う。preflight は plan の `variants[].stock` に自動で `0` を入れる
(質問しない)。

## 「質問しない」の範囲(最初に依頼者へ伝える)

- **業務判断(価格・納期・コピー元・公開範囲)は、着手時にすべて聞く。** 承認後は聞かない
  (在庫数は上記の通り常に0で質問しない)。
- ただし次の**運用上の停止**は起こりうる。これは質問ではなく「安全のための停止」で、開始時に必ず知らせる:
  1. Eストア管理画面のセッション切れ(ログインコマンドを1回実行してもらう)
  2. Yahoo!の未反映が下見のときより増えていた(他の担当者の編集が混ざる恐れ。反映せず停止)
  3. GoQ の行を一意に決められない(バリエーション初回に起こりやすい)
  4. 外部システムの一時的な失敗
- 途中で聞くことになった項目があれば、「最初に聞き漏らした」として最終報告に書く(質問リストを直すため)。

- 023 本番サーバー `127.0.0.1:8290` が応答する(`curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:8290/api/goq/status`)
- 商品は**楽天RMSに登録済み**であること(楽天には新規作成APIが無い。無ければここで止めて依頼者へ)
- 正本DBは `023.商品マスタDB/data/productmaster.db`(`C:/ProductMaster/productmaster.db` は空ファイルなので使わない)

3. 続けて **AskUserQuestion(クリック形式)で、次を1回にまとめて聞く**(在庫数は聞かない・常に0):
   | 質問 | 選択肢 |
   |---|---|
   | Eストア価格・納期 | 既定=楽天税込価格÷1.1、納期5日。`flags` に端数があれば丸め方も聞く |

   | 公開の範囲 | 「Eストア公開+Yahoo!公開・店頭反映」/「Yahoo!の反映は人が行う」/「非公開のまま登録」。**Yahoo!の店頭反映はストア全体の未反映分を一緒に公開する**と一言添える。下見で他の未反映があれば件数を示し、「反映は人が行う」を推奨する |
   **Yahoo!のコピー元=紐付くパス(2026-09-28 G2231 でユーザー指摘・必須)**: コピー元から引き継ぐのは
   **path(ストア内カテゴリ)と product_category だけ**で、名前・価格・説明文は楽天の内容が入る。したがって
   コピー元は価格ではなく**どのフォルダに紐付くか**で選ぶ。`yahoo_copy_candidates` は同じパス集合ごとに
   まとめた一覧(`org_paths`=艦・部隊の紐付き先、`paths`=全文、`count`、`thin_path`)を返すので、Claude が
   商品の中身(護衛艦/潜水艦/陸上部隊/航空部隊/帝国海軍…)に合う `org_paths` のグループを選んで提示する。
   別の艦・部隊のフォルダ(例: 部隊ワッペンを「護衛艦たかなみ」へ)に紐付く候補を推奨しない。ぴったりの
   フォルダが無ければ、上位の汎用フォルダ(例: `海上自衛隊:陸上部隊` や `海上自衛隊` まで)の候補を推奨する。
   パスが「【ネコポス可】」だけの候補(`thin_path`)は、ワッペン等のカテゴリにも組織フォルダにも出ないので
   推奨しない(`approve` が拒否する。意図的なら `yahoo.allow_thin_path: true`)。
4. 答えを `draft_plan` に反映して plan を確定する(`estore_product_name`・`estore_price`・

   Python か Edit で JSON を直接直す。`estore_product_name` は**楽天の title と同一だと弾かれる**

5. **確認画面(アーティファクト)を1つだけ出し、承認を1回取る。** JSON ではなく、店の担当者が読める日本語で:

   公開範囲(何がお客様に見えるか)・Yahoo!のコピー元・登録される全SKU・**対象外(Amazon/LCL/7S)**・

6. 承認を得たら plan に承認を刻む(24時間有効。承認後に plan を編集すると無効になる):

   これは認証ではなく整合性チェック(ハッシュ)。**承認を取る責任は Claude 側にある**(承認前に実行しない)。

## Phase 1: 実行(承認後は自動)

```bash
python C:/ClaudeCode/.claude/skills/register-product/pipeline.py run --plan <plan.json>
```

各ステップは「済んでいれば SKIP → 実行 → 結果の状態を読み戻して検証」。落ちても同じコマンドで再開できる。
完了済みの plan は再実行を拒否する(**`--only` を付けても拒否される**。確認だけなら `verify`、意図した
再確認・再実行は `--reconcile`)。同じ plan の二重起動はロックで拒否する(実行中プロセスの生死を確認し、
死んでいれば経過時間に関係なく即座に回収する)。NEEDS_USER で止まった plan は、内容を直して再度
`approve` すれば(完了前なので)そのまま再開できる — 承認ハッシュが変わっても、完了済みでなければ拒否しない。

| step | 内容 | 検証・SKIP の根拠 |
|---|---|---|
| import | 楽天→023 取込(画像込み) | 子SKUの集合が plan と一致・画像あり |
| prices | `estore_price`(親・子)・納期・**Eストア表示名**を PATCH | 親と全子を読み戻して一致(表示名も) |
| estore_register | Eストアへ非表示で新規登録+画像FTP | final_status=ok・画像失敗0 |
| estore_images | 画像台帳CSVの往復(保存セッションでブラウザ操作) | 023 の紐付け記録で SKIP 判定。CSV の画像名が対象SKUの送信済み画像と**完全一致**のときだけ送る |
| estore_bind | 画像を商品に紐付け | 023 の `bound_at` が全画像で埋まる |
| estore_publish | 公開(display=Yes+陳列期間解除) | `estore_status=public` |
| yahoo_register | Yahoo!へ登録(コピー元指定・画像・在庫枠) | 読み戻し(失敗は停止): display・説明文・送料グループ・**パスが承認時のコピー元と一致** |
| yahoo_reserve | 店頭反映(ストア全体) | 店頭に出ていれば SKIP。未反映が下見+許容を超えていれば**停止**。反映後は店頭ページが開くまで最大3分 |
| goq_resync | GoQ在庫連携(キュー経由・ログイン失敗は1回だけ再実行) | 連携判定が全モール True(判定はキューが空になった後のCSV取込で作られるので、判定行ができるまで最大5分待つ) |
| goq_stock | GoQ総在庫数を1行ずつ書く(行ID指定) | 行数=variant数・1対1対応・job の `changed_fields==["stock[<行ID>]"]`(実際に変わった行が対象の1行だけ)。行ごとの進捗を state に保存 |
| verify | 店頭(Eストア・Yahoo!)と GoQ の最終確認 | 商品名・価格・画像の参照・Yahoo!のパス・連携判定 |

出力は 1行1ステップ `STEP <名前>: OK|SKIP|FAIL|NEEDS_USER <詳細>`。終了コード 0=完了 / 1=失敗 / 10=ユーザー操作が要る。
**SKIP は「済みなので飛ばした」であって、内容が正しい保証ではない。** 内容の確認は verify が行う。

### FAIL のときは

- その場で作り替えたり、別手段で押し込まない。FAIL の原因・どこまで済んだか(state ファイル
  `<plan>.state.json`)・次の一手を報告する。原因が外部AI/ハーネス由来なら `incident_log.py add` で台帳に1行残す。
- **通信エラーで書き込み系が落ちたときは、サーバー側の状態を確認してから再実行する**(成功していて応答だけ届かなかった可能性がある)。

## 実装・運用メモ(G2225 で実測した事実)

- 楽天の manageNumber は**小文字**(`g2225`)。大文字は 400。023 の SKU は大文字(`G2225`)。バリエーション商品の親は `{G番号}-parent`。
- Eストア価格 = 楽天税込価格 ÷ 1.1(G2223: 1694→1540、G2224: 1815→1650)。納期は既存品と同じ5日。
- **Eストア表示名は楽天の商品名(長い・SEO詰め込み)と別に、短い名前を持つのが既存の慣習。**
  実例: `ワッペン(軍艦旗＆戦艦大和)ベルクロ付`(19文字)・`Tシャツ(海上自衛隊・ドルフィンマークワッペン)`
  (24文字)・`部隊識別帽(海上自衛隊 練習艦しまかぜ)アゴヒモ付き`(26文字)。楽天の元名は44〜90文字程度あり、
  そのまま使うと後で管理画面から手動修正することになる(G2225 2026-09-25 実例。修正は023を経由せず直接
  行われたため、023の記録は古い長い名前のまま残った)。**技術的な文字数上限ではなく業務上の慣習**
  なので、Amazon item_name と同じく毎回 Claude が候補案を作りユーザーに選んでもらう(自動生成しない)。
- **023 の在庫欄(`products.stock`)は API で書けない**(GoQ・モール側が正)。在庫数は GoQ に書く。
- 画像台帳CSVは**全件ダンプではなく「未登録画像のリスト」**。再アップロードは追記型で既存画像を消さない。
- Yahoo!の `register-new` は `publish` を指定できる。`publish=true` で display=1 で登録し、店頭に出るのは店頭反映の後。
  既存の `set_display`(表示だけ切り替える関数)は、送っていない項目を空で上書きする危険があるので使わない。
- Yahoo!の店頭反映は**ストア全体**を公開する。Yahoo! API は未反映の「件数」しか返さず、商品の一覧は取れない。
  パイプラインは下見の件数との差で他の担当者の編集を検知する(件数が同じで中身が入れ替わる場合は検知できない)。
- Yahoo!の商品コードは楽天の manageNumber(小文字)。Eストアの商品コードは G番号(親の `-parent` は付かない)。
- GoQ の操作は必ず `/api/queue/*` 経由。GoQ検索は別チャネルの行まで拾うことがあるため、在庫数は `row_ids` 指定で書く。
- GoQ連携判定のキーは、単品なら SKU、バリエーションなら `{G番号}-parent`。

## 既知の限界(隠さず報告する。2026-09-28 cgd Lv3 健全性チェックで再確認・未解決のまま残っている論点)

Codex+DeepSeek の技術×批評4レビューで、これらは**構造的な未解決課題**として指摘された
(実装の書き間違いではなく、仕様として人が決めるべき論点)。下記2点は**ユーザーに確認済み**
(2026-09-28)で、現状の仕組みのまま進めてよいとの判断。理由も併せて記録する。

- **公開から在庫設定までの間、Eストアが「在庫切れ」表示になる。** バリエーション商品で `goq_stock` が
  NEEDS_USER で止まった場合は、人が対応するまで在庫0の公開商品が残る。
  → **ユーザー判断(2026-09-28): 現状のままでよい。** 在庫0だと購入できないため、それ自体が
  フェイルセーフとして機能している(誤った内容で売れてしまう事故を防ぐ側に倒れる)。公開順序を
  変える改修は行わない。
- **Yahoo!の店頭反映(店全体を公開する操作)の安全策は「件数の増減を見る」までで、内容の入れ替わりは
  検知できない。** `pending_allow` の値に業務上の根拠は無く、閾値をすり抜ける衝突が理論上ありうる。
  → **ユーザー判断(2026-09-28): 現状の自動反映のままでよい。** 「常に人がストアクリエイターPro
  で反映する」への変更は行わない。
- GoQ の在庫数は、書き込みジョブの返り値で確認しており、GoQ 画面から数量を読み戻してはいない。
- GoQ の行特定は、GoQ側が列構造のデータを返さず(検索結果は1行あたり「チェックボックス値+説明文
  テキスト200文字」のみ。`goq_browser.py` のスクレイピング実装に起因)、完全一致ではなく語境界つきの
  部分一致に留まる(2026-09-28 に "M" が "ML" に誤一致する等の粗さは直したが、原理的な限界は残る)。
- ロールバック手段は無い(誤って公開・在庫を書いた場合は手で戻す)。dry-run(テスト商品で1周)も無い。
- 承認ハッシュは認証ではない。plan ファイルを直接書けば本番書き込みを起動できる。
- Yahoo!の価格・画像・送料・バリエーション軸の最終確認は限定的(display・説明文有無・送料区分のみ)。
  GoQ の実在庫数も読み戻していない。「販売できる状態」の保証範囲は verify が見ている項目に限られる。
- テストは判定ロジック(`validate_plan`・ロック・承認・GoQ行特定等)のみ。実際の HTTP 書き込みを伴う
  各 step 関数(`step_prices`・`step_estore_register` 等)自体は自動テストで検証していない
  (モックの仕組みが無いため。G2225 での実機確認が現状唯一の裏付け)。

## バリエーション商品(Tシャツ等)の位置づけ — 試験運用

コードは単品・バリエーション両対応だが、**実機で通したのは単品(G2225)だけ**。初回のバリエーション登録は
「試験運用」として着手時に依頼者へ伝え、次の3点を確認しながら進める(結果は最終報告に明記):

**ユーザー判断(2026-09-28): このまま(本番の店頭で初回を試す・ロールバック手段なし)で進めてよい。**
公開順序・Yahoo!全店反映の2点と合わせて、追加の安全策(非公開までで止める等)は導入しない方針。
G2230 が初のバリエーション実機テストになる。

1. `prices`: 子SKUごとの `estore_price` が入り、読み戻せる
2. `yahoo_register`: 軸(options/sub-code)付きの登録が通る(既存の `register_new_item` の経路)。**軸名・選択肢・variant数の読み戻しは未実装**なので、店頭で目視確認する
3. `goq_stock`: GoQ の行数が variant 数と一致し、色・サイズの文字で一意に対応する(しなければ NEEDS_USER)

## 2026-09-28 の健全性チェック(cgd Lv3・第2回)で直した実装バグ

「前回Lv3の指摘が正しく実装されているか」の点検で、**実装漏れ・骨抜きが複数見つかり**修正した:

- 🔴 **(初のバリエーション実機登録・G2230 で発覚) `yahoo_copy_candidates` が変化のある商品では常に
  0件を返していた** — Yahoo!側の実データは `yahoo_snapshot_products.variation{1-5}_name` 列に
  軸名を入れておらず(サイズ違いのsub-codeを実際に持つ商品でも全列NULL/空文字)、軸数の完全一致を
  求める旧ロジックはバリエーション商品で候補が絶対に見つからなかった。判定を
  `yahoo_snapshot_variants` の実データ(sub-code の有無)基準に直した
- 🔴 **`step_verify` が Eストアの照合に楽天の長い商品名を使っていた** — 前日導入した短縮表示名
  (`estore_product_name`)と噛み合っておらず、正常に登録できていても verify が必ず FAIL していた
  (G2225 の実データで再現・修正後に解消を確認済み)
- 🔴 **`--only` を付けると完了済み plan の再実行拒否が丸ごと素通りしていた** — `--only goq_stock` 等の
  書き込み系ステップを、完了済みの plan に対して単発で再実行できてしまっていた。あわせて、存在しない
  ステップ名を指定すると何もせず終了コード0(成功)を返す欠陥も修正
- 🔴 **承認ハッシュの不一致を無条件で拒否しており、SKILL.md が案内する「NEEDS_USER→plan を直して
  承認し直して再開」という正規の手順が実装上成立していなかった** — 完了前の plan であれば、内容を
  変えて再承認しても再開できるよう修正(完了済みかどうかは各ステップの実際の状態で判定する)
- 🟠 Eストア対象外(`estore.register=false`)でも `estore_product_name` を無条件で PATCH しており、
  既存の値を意図せず消しうる状態だった → 対象外なら触れないよう修正
- 🟠 ロックが `os.open(O_CREAT|O_EXCL)` の競合例外を捕捉しておらず、また経過時間だけで stale 判定して
  いた(実行中プロセスでも 2 時間で奪われうる)→ PID の生存確認(Windows・ctypes)を優先し、確認できな
  い場合だけ経過時間にフォールバックするよう修正
- 🟡 GoQ の行特定が完全な部分文字列一致で、"M" が "ML" に誤ヒットしうる状態だった → 英数字トークンは
  前後が英数字でない位置での一致を要求するよう修正(日本語トークンは GoQ 側の生データが列構造を持たない
  ため単純な部分一致のまま。既知の限界として残す)
- 🟡 state 保存が非アトミックで、書込み途中の終了で JSON が壊れると再開不能になりうる → 一時ファイル
  経由の置換に修正
- 🟡 承認日時が未来・形式不正でも通っていた/plan の bool 項目に文字列を入れても通っていた
  (Python は `"false"` を真扱いするため)/バリエーションで variant 間の軸構成が違っても通っていた
  → いずれも validate_plan で弾くよう修正
- 追加: 承認後に楽天RMS側の内容(価格・画像・variant構成)が変わっていないかを、`import` ステップの
  冒頭で指紋照合するようにした(023 既存の `rakuten_sync.canonical_hash` を再利用)
- 単体テストを 24→42 件に拡充(上記の回帰テストを含む)

**3点ともユーザーに確認済み(2026-09-28)**: いずれも現状の仕組みのままでよいとの判断(詳細・理由は上の
「既知の限界」節に記録)。追加の安全策(公開順序の反転・Yahoo!反映の完全人力化・バリエーションの試験

## 2026-09-28 追記: G2230(初のバリエーション実機登録)で判明した追加の不具合・運用メモ

- 🔴 **`yahoo_copy_candidates` の判定バグは既に上で直した版が対象。バリエーション商品では検証まで
  0件のままだった実例が G2230 で発生**(上記参照)。
- **Yahoo!のコピー元候補が、023の`yahoo_snapshot_products`に未取込のことがある。** Yahoo!上に実在する
  商品でも、CSVスナップショットへの取込漏れで候補に出ない/`register-new`が「snapshotに存在しません」
  で拒否されることがある。対処: `yahoo_shopping_api.get_item()` でライブ取得し、`path`(改行結合)と
  `product_category` を中心に `yahoo_snapshot_products` へ upsert する(`register_new_item`が実際に
  コピーするのはこの2列だけ。`COPY_FIELDS`参照)。手順は都度その場で組んだ簡易スクリプトで対応しており、
  本スキルの正式なコマンドとしては未整備(再発したら都度同じ手順を踏む)。
- **在庫数は常に0で登録する(絶対ルール)。** 質問を廃止し、preflightが自動で0を入れるよう修正済み
  (上の「在庫数は必ず0で登録する」節)。
- 🔴 **023既存の `yahoo_shopping_api.get_item()` 自体にバグがあった(本スキル固有ではない)。**
  docstringは「該当商品なしは found=False で返す(例外化しない)」と謳うが、実装はHTTP 400を無条件で
  例外化しており、**新規登録前の「登録済みか確認する」という最も基本的な呼び出しで必ず失敗する**状態
  だった。Yahoo!は未登録item_codeに `HTTP 400 + <Error><Code>it-05002</Code>` を返す。この特定コード
  のときだけ found=False を返すよう `server/services/yahoo_shopping_api.py` を修正した
  (`023.商品マスタDB/tests/test_yahoo_shopping_api_get_item.py` にテスト追加)。既存呼び出し元
  (display確認等)への影響なし(見つかった場合の戻り値の形は変更していない)。
- 🔴 **`step_goq_stock` の検証が `row_count==1` を要求しており、バリエーション商品で必ず FAIL していた。**
  `row_count` は「反映画面で選択された全行数」であり、`row_ids` で絞っても検索にヒットした行数
  (variant数)がそのまま入る(goq_worker.set_quantity の「選択チェックボックスは全行必須」という仕様の
  帰結)。実際に変更された行は `changed_fields`(例: `["stock[175572]"]`)で判定するよう修正した。
  実際の書き込み自体は当初から正しく1行だけに限定されており、誤書き込みではなく誤検証だった。

## 2026-09-28 追記: G2231 で判明した Yahoo!コピー元の選び方の誤り

- 🔴 **旧 `yahoo_copy_candidates` は「同価格・新しい順」で候補を出しており、パスを見ていなかった。**
  コピーされるのはパスとカテゴリだけなので、価格は判断材料にならない。実際に上位に出ていた
  g2225・g2223・g2207 は Yahoo! の現物でもパスが「【ネコポス可】」1本だけで、ワッペンのカテゴリにも
  海上自衛隊のフォルダにも出ない。**G2225 はこの候補(g2223)をコピー元にして登録したため、同じ状態で
  Yahoo! に出ている**(2026-09-28 時点で未修正。直すにはストアクリエイターProでパスを付け直す。
  editItem は送らない項目を空で上書きするので API で部分修正しない)。
- 修正: 候補をパス集合ごとにまとめ、パス全文を返す/【ネコポス可】だけの候補は末尾に回し、`approve` で拒否/
  承認時にパスを固定し、登録後に Yahoo! の実物と照合する。`yahoo_publish_tool.py item` が `paths`・
  `product_category` を返すようにした。
- 🟠 **`goq_resync` が連携判定を20秒しか待っていなかった。** 判定(`goq_sync_status`)は GoQ 連携ジョブ
  自体では作られず、キューが空になった後にサーバーが連携表CSVを出力→023へ取り込んだときに作られる
  (`job_queue._worker_loop`)。G2230 は約30秒後の取込にたまたま間に合い、G2231 は約84秒かかって
  「判定なし」で FAIL した(連携自体は成功していた)。判定行ができるまで最大5分待つよう修正。
- G2231 は g2134(第2術科学校ワッペン)をコピー元にし、`海上自衛隊:陸上部隊` とワッペンのカテゴリに
  紐付いたことを実物で確認した(9本一致)。
