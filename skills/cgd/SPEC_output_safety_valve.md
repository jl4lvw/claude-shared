# 指示書 — cgd の外部エンジンに「出力の安全弁」を入れる

作成: 2026-08-12 / 起案: /cgd Lv3 レビュー（Codex ×2 + DeepSeek ×2）で **4 者中 3 者が最優先**に挙げた項目
対象セッション: これ単体で実装できるように書いてある。**この文書だけ読めば足りる**。

---

## 1. 何が起きているか（実測）

2026-08-12、`/cgd Lv2` で 26KB の差分を DeepSeek reviewer にレビューさせたところ、

```
[DS Usage] 今回: 入力 7,677 (miss) + 1,280 (hit) / 出力 31,999 tok (¥1.51 / $0.0100)
WARNING: 出力が上限(32000 tok)で打ち切られました。
ERROR: 本文が空です(finish_reason=length)。推論だけで出力予算を使い切った可能性があります。
(参考: reasoning は 111701 文字ありました)
```

**¥1.51 を払って、レビュー結果が 1 文字も返らなかった。**
`reasoning` に 111,701 文字が生成されていたが、**すべて捨てられた**。

同じ差分・同じ DeepSeek を `/pv --mode review`（JSON の構造化出力を要求する側）へ投げた場合は、
出力 2,065 tok・¥0.28 で 9 件の指摘が正常に返っている。つまり
**「自由記述で書かせると reasoning が暴走して予算を食い尽くす」**という failure mode がある。

### なぜ重大か

- cgd Lv1-3 には**成果物が揃ったかの機械判定が無い**。この失敗は「レビュー結果ゼロ」として
  静かに統合表へ流れうる（今回は ERROR が出たので気づけたが、運用者が気づく保証は無い）
- Lv1-3 の実績は 16 日で 30 回ある。**そのうち何回が空出力だったかは分かっていない**
- 費用は「生成した分だけ」課金される。**失敗しても満額取られる**

## 3. 要件

### MUST（これが無いと目的を満たさない）

1. **本文が空になったとき、自動で 1 回だけリトライする。**
   - リトライ時は `max_tokens` を引き上げる（**同じ設定で繰り返さない**）
   - リトライは **1 回まで**。2 回目以降は絶対に自動で回さない
   - リトライしたことを stderr に明示する（何回・どの設定で回したか）

2. **`reasoning_content` を捨てない。**
   - 本文が空でも、reasoning があれば**それを成果物として救出する**
   - ただし本文と混同させない。stdout へ出すなら明確な見出しを付ける
     （例: `## [reasoning からの救出 — これは最終回答ではありません]`）
   - 111,701 文字をそのまま出すと呼び出し側の context を壊すので、**上限を設けて切る**

3. **どんな場合でも stdout に最低 1 行は出す。**
   - 現状は本文が空だと stdout が完全に空になる。呼び出し側は
     「指摘なし」と「実行失敗」を区別できない
   - 失敗時は **構造化された失敗レポート**を stdout に出す（下記フォーマット案）
   - **exit code は非 0 のまま**（成功に見せない）

4. **exit code を専用の値にする。**
   - 「本文が空（予算枯渇）」は auth でも timeout でもない。`EXIT_GENERIC`(1) では
     他の汎用エラーと区別できず、呼び出し側が自動判断できない
   - 新設するか既存に寄せるかは実装者判断。**決めたら 3 本すべてで揃える**

### SHOULD（あると良い）

5. **入力サイズから `max_tokens` を自動調整する。**
   実測では入力 8,957 tok で reasoning が予算 32,000 を使い切った。
   入力が大きいほど reasoning が伸びる傾向があるので、初回から余裕を持たせる。
   API は 65,536 まで受理することが実測済み（`deepseek_coder.py` のコメントに記録あり）。

6. **`gemini_advisor.py` にも同じ手当てを入れる。**（構造が同じなら）

### WON'T（やらないこと）

- **無制限のリトライ。** 失敗のたびに満額課金されるので、費用が青天井になる
- **本文が空でも exit 0 にする。** 「指摘なし」と誤解される経路を作らない
- **reasoning を本文として返す。** 中間思考であって回答ではない。混ぜたら検証が壊れる

## 4. 設計の選択肢（実装者が選ぶ）

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| **A: 自動リトライ**（推奨） | 空を検出したら `max_tokens` を上げて 1 回だけ再実行 | 呼び出し側の手を煩わせない。今回のような取りこぼしが消える | **費用が二重にかかる**（1 回目の ¥1.51 は戻らない） |
| B: 出力形式の構造化 | プロンプト側で JSON など短い形式を要求し、reasoning の暴走自体を抑える | 根本対策。pv 側で実際に効いている（同一差分で 2,065 tok に収まった） | cgd の自由記述レビューという性質を変えることになる。影響範囲が広い |
| C: 入力の分割 | 大きい入力を分けて複数回呼ぶ | 予算枯渇を構造的に避けられる | 分割の判断が難しく、指摘が分断される |

**推奨は A + 5（入力サイズからの初期値調整）の組み合わせ。**
B は本質的だが cgd の設計思想（自由記述で深く書かせる）に触れるので、
**別の判断として切り離す**。この指示書では A を実装する。

> 実装者へ: A を選んだ場合でも、**B が本筋である可能性**は報告に残すこと。
> 「同じ入力・同じモデルで、構造化出力を要求した pv 側は 1/15 のトークンで完走した」
> という実測がある。

## 5. 失敗レポートの出力フォーマット（案）

本文が空でリトライも失敗した場合、stdout に次を出す（呼び出し側が機械的に扱えるように）:

```
[ENGINE_FAILURE] engine=deepseek role=reviewer reason=empty_body finish_reason=length
attempts=2 max_tokens_used=32000,65536 input_tokens=8957 reasoning_chars=111701

## この呼び出しは失敗しました
- 本文が生成されませんでした（推論だけで出力予算を使い切っています）
- **これは「指摘なし」ではありません。** 統合表に「指摘なし」と書かないでください
- 対処: 入力を分割するか、出力形式を構造化して短く書かせてください

## [reasoning からの救出 — これは最終回答ではありません]
<先頭 N 文字>
```

- 1 行目を機械可読にしておくと、cgd の Workflow / 将来の collect が判定に使える
- `N` は実装者判断（2,000〜4,000 文字程度を想定）

## 9. この作業での注意（過去に踏んだ罠）

- **既存ファイルの編集前に必ずバックアップ**: `cp file file.bak_$(date +%Y%m%d_%H%M%S)`
- **`encoding="utf-8"` を明示**。書き戻しは `newline=""` を付ける
  （付けないと Windows で LF が CRLF に黙って変換される）
- **シバン行（`#!/usr/bin/env python3`）を書かない**（Windows で py.exe が即終了する）
- **heredoc で Python を流し込んで文字列置換しない。**
  `\n` が実際の改行に、`\b` が 0x08 に化ける事故が 2026-08-12 だけで 5 回起きている。
  **修正スクリプトは Write ツールでファイルに書いてから実行する**
- **文字列置換は空振りする。** 「置換した」と思い込んだ箇所が実際は変わっていない事故が
  同日 2 回起きた。**置換後は必ず実物を読んで確認する**
- **別セッションが同じファイルを同時に編集していることがある。** 差分を取るときは
  自分が変えていない箇所が混ざっていないか確認する

## 11. 依頼者への確認が要る点（実装前に聞くこと）

1. **リトライで費用が二重にかかることを許容するか。**
   1 回目 ¥1.51 + 2 回目（さらに大きい予算）で、失敗時の損失は増える。
   「リトライせず、失敗レポートだけ出して止める」という選択もありうる。
2. **`max_tokens` の上限をいくつにするか。** API は 65,536 まで受理する実測があるが、
   上げるほど「失敗したときの損失」が増える。
3. **案 B（出力形式の構造化）を別途検討するか。** 本質的な対策はこちらの可能性が高い。
