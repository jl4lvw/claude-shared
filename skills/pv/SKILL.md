# pv — 並列検討・検証（parallel verify）

複数の担当（視点）に同じテーマを並列で当て、**Fable 5 が取りまとめる**。
`/cgd` がコードの良し悪しを見るのに対し、pv は **「この方針で正しいか」「何を見落としているか」** を見る。

## 🚦 レベル番号だけ言われたら「cgd のレベル」（2026-08-12 ユーザー決定）

ユーザーが「レベル4で」「Lv8 で」のように**どのスキルか言わずにレベルだけ**伝えた場合、
**常に cgd のレベルとして解釈する。** pv のレベルとして解釈してはいけない。

**pv は Lv1〜Lv3（検討）のみ。実装フェーズは持たない。** Lv4 以降を pv に足す案は
2026-08-12 に cgd Lv3（Codex + DeepSeek × 技術・批評の 4 レビュー）へかけ、
**4 者全員が反対**したため取り下げた。理由:

- cgd が既に Lv4-8 で実装を持っており、**同じ Lv 番号で意味が違うと選べない**
- 実装内容の妥当性は非 LLM では測れず、`sha256 が変わった`／`import が通る` は
  「触った事実」の検査にすぎない。**pv の「LLM に判断させない」思想を守ったことにならない**
- 「一覧外のファイルが変更されていない」検証は、並行編集環境では**原理的に成立しない**

### 検討結果を実装へ渡すとき

`raw/merge.md`（統合結果の全文）と `raw/*.md`（各担当の回答）を cgd のレビュー入力に添える。
統合結果には nonce と逐語引用が入っているので、**どの担当の発言に基づく結論か**が追える。

## /cgd との使い分け（責務境界）

> **選ぶ軸は「速さ」対「確からしさ」（2026-08-12 ユーザー決定）**
>
> | 場面 | 選ぶもの |
> |---|---|
> | **軽量に・早く**対応したい | **cgd Lv1-3**（inline 並列・数分・準備は 1 ファイル） |
> | **Workflow を使って高度に判断**したい | **pv**（決定論的な依頼文・非 LLM ゲート・context 節約・十数分） |
>
> **pv は cgd の速い版ではない。** 手数と待ち時間を払って確からしさを買うレーン。
> 重なって見える範囲があるのは意図的で、**どちらかを廃止する予定はない**。

| | `/pv` | `/cgd` |
|---|---|---|
| 対象 | 仕様・設計・方針・進め方の検討 | 差分・実装コードのレビュー |
| 出力 | 一致点 / 食い違い / 片側だけの指摘 / 未解明 | 指摘表（🔴🟠🟡）+ 実装フロー |
| 実装 | **しない**（検討で終わる） | Lv4 以上は実装・検証・再レビューまで |
| 取りまとめ | **必ず Fable 5** | Claude 本体 |

> 将来的に両者の並列実行部を共通エンジンへ寄せる案がある（2026-08-11 の Lv3 レビューで
> 4 者中 3 者が「独立させる必然性が弱い」と指摘）。当面は別スキルとして運用し、
> pv が実運用に耐えると分かった時点で統合を再検討する。

## 🚨 絶対に守ること

1. **必ず Workflow を使う。** inline で担当を回す経路は用意していない
2. **依頼テキストを自分で書かない。** `pv_plan.py` が生成したものを使う
3. **Workflow の args は `build` が出力した JSON をそのまま渡す。** 手で組み立てない
4. **Workflow 完了後、主 context が自分で `collect --include-merge` を叩く**（後述・唯一の非 LLM ゲート）
5. **`build` に `--skill-version` を渡す。** 渡さない／古いと build が止まる（版ずれ検出）
6. **run が終わったら `pv_usage_log.py record` を叩く。** 成功でも失敗でも残す

## 手順

### Step 1: テーマをファイルに書く

主 context が「テーマ本文」を書くのはここ **1 回だけ**。以降は Python が扱う。

```bash
cat > "C:/tmp-ai/pv_topic.txt" <<'EOF'
【テーマ】<何を検討したいか>
【背景】<なぜ検討するか・現状>
【判断したいこと】<この検討で決めたいこと>
EOF
```

### Step 2: プランを生成する

```bash
python "C:/ClaudeCode/.claude/tools/pv_plan.py" build --level 2 --topic-file "C:/tmp-ai/pv_topic.txt" --depth mid --skill-version <冒頭スタンプ>
```

`--skill-version` には、**いま自分の context にある冒頭スタンプの値**を渡す。
ディスク上の値と違えば build は非 0 で止まる（版ずれ検出・後述）。

**検証対象の実体があるなら必ず `--attach` で渡す**（複数可・合計 200KB まで）:

```bash
python "C:/ClaudeCode/.claude/tools/pv_plan.py" build --level 3 --topic-file "C:/tmp-ai/pv_topic.txt" --skill-version <冒頭スタンプ>   --attach "C:/path/to/target.py" --attach "C:/tmp-ai/diff.patch"
```

添付は Python が読んで依頼文へ埋め込む。**外部エンジン（DeepSeek / Codex）はファイルに
アクセスできないので、埋め込む以外に実体を渡す手段が無い。** 添付が無いと担当は
テーマ本文の抽象論しか扱えず、実体との食い違いを検出できない。

出力の 2 行目 `WORKFLOW_ARGS ` の後ろの JSON が、そのまま Workflow の args になる。

- 既存 run の回答が残っている場合は **停止する**（`--force` で消して作り直す）
- 未実装レベルを指定すると停止する

### Step 3: Workflow を起動する

```
Workflow({ scriptPath: "C:/ClaudeCode/.claude/skills/pv/workflows/pv_run.js",
           args: <WORKFLOW_ARGS の JSON をそのまま> })
```

**キー名を手で書き直さないこと。** 過去に args のキー名取り違えで、無関係な古いファイルを
4 回連続でレビューし続ける事故が起きている（だから `build` が args ごと出力している）。

### Step 4: 主 context が自分で検証する（**省略禁止**）

```bash
python "C:/ClaudeCode/.claude/tools/pv_plan.py" collect --run <RUN> --include-merge
```

- **exit 0 を確認してから結果を採用する**
- Workflow 内の Verify フェーズも同じコマンドを叩くが、**あれは LLM 経由**である。
  Workflow スクリプトは Bash を持てないため、これが構造的な上限になっている。
  ここで主 context が自分で叩くことが、**唯一の非 LLM ゲート**
- **忘れても気づけるようにしてある**: `build` が `<run>/.pending_verify` を置き、
  `UserPromptSubmit` hook (`pv_verify_reminder.py`) が未検証の run を毎ターン提示する。
  印が消えるのは `collect --include-merge` が exit 0 したときだけ。
  **遮断はしない**（run は数分かかるので、走行中に作業を止める害の方が大きい）


**この collect は 3 つを同時にやる**（2026-08-12 に一元化）:

1. 成果物が揃っているかの判定（存在・サイズ・構造・降参文）
2. **統合の実在検証** — 統合結果に各 raw の `[pv-token:...]` と
   **raw からの 30 文字以上の逐語引用**（`[pv-cite:<id>]`）があるかを機械照合する。
   トークンは raw の中にしか無いので、揃っていれば統合役は全 raw を開いている
3. 統合実績の自動記録（Step 5）

> **なぜ引用まで要るか**: 私は当初「merge の mtime が raw より新しいこと」を提案したが、
> Lv8 の 4 者に「それは**後から書いたっぽい**証明でしかなく、読んだ証明にならない」と
> 却下された。実際に「統合役が raw を読まずに書いた merge」を作って試すと、
> 従来の判定（サイズ・構造）は素通りし、トークン照合だけが検出した。
>
> **限界も書いておく**: これは「開いて引用した」証明であって「理解した」証明ではない。
> 内容の妥当性は非 LLM では測れない。

### Step 5: 記録は自動（手で叩くものは無くなった）

**2026-08-12 の cgd Lv8 レビューを受けて、手動 `record` は廃止した。**
Step 4 の `collect --include-merge` が exit 0 になった時点で、Python が
統合実績（使用モデル・統合結果のサイズ・引用検証の結果）を自動記録する。

理由: 「Workflow 完了後に record を叩く」を必須手順にする案は、
**cgd と同じ忘却構造のまま**だと 4 者から却下された。記録を「印を消す唯一の場所」に
寄せることで、記録が残っていない run は印も消えない、という関係にした。

### Step 6: 結果を提示する

- 一致点 / 食い違い / 片側だけの指摘 / 未解明 を分けて出す
- **食い違いは raw ファイルで裏取りしてから採用する**（統合結果を鵜呑みにしない）
- 使われた取りまとめモデル（`merge_model_used`）を必ず書く。fallback が発火したら明記する

## レベル（`--level`）

| Lv | 構成 | 状態 |
|---|---|---|
| 1 | 軽量 — Claude 2 視点（棚卸し / 反証）+ Fable 統合 | **実装済み** |
| 2 | 標準 — Claude 2 視点 + **DeepSeek 1 視点（外部視点）** + Fable 統合 | **実装済み** |
| 3 | 技術 — Claude 2 視点 + DeepSeek + **Codex 1 視点（実現性）** + Fable 統合 | **実装済み** |
| 4 以降 | **pv には無い** | 指定すると停止し、`/cgd` の Lv4 以降へ案内する |

エンジンは `mode` で扱いが分かれる:

| mode | エンジン | 誰が答えるか | raw を書くのは |
|---|---|---|---|
| `self` | Claude | agent 自身 | agent（Write） |
| `exec` | DeepSeek / Codex | 外部 CLI | **Python**（agent は要約のみ） |

`exec` の担当エージェントには「**自分で考えた内容を混ぜるな・失敗しても代わりに答えるな**」と
指示している。外部エンジンが落ちたときに Claude が肩代わりすると、
「DeepSeek の意見」として Claude の意見が混入するため。

## 深さ（`--depth`）— レベルと直交

| depth | Claude effort | DeepSeek model | Codex reasoning |
|---|---|---|---|
| low | low | deepseek-v4-flash | low |
| mid（既定） | medium | deepseek-v4-flash | medium |
| high | high | **deepseek-v4-pro**（料金 3 倍弱） | high |

外部エンジンのタイムアウトは**エンジン別**（codex 600 秒 / deepseek 300 秒）。
codex は reasoning=high で 10 分かかることがあり、一律 300 秒だと理由なく落ちる。
`exec --timeout` で個別に上書きできる。

**Codex には探索させない。** 実測モデル（2026-08-11）では `tokens ≒ 14,000 + 0.75×入力バイト + 約3,000×探索回数` で、
探索が消費の大半を占める。pv のテーマは文章でありリポジトリではないので、依頼文だけで答えさせている。

**回す前に `env`、詰まったら `doctor`。** 別物なので混同しない。

```bash
python "C:/ClaudeCode/.claude/tools/pv_plan.py" env            # 環境（鍵・CLI・テンプレ・WF）
python "C:/ClaudeCode/.claude/tools/pv_plan.py" doctor --run <RUN>   # その run の状態
```

`env` は cgd の `cgd_doctor.py` に相当する。鍵と CLI の不在が「外部エンジンが落ちた」の
大半を占めるので、run を作る前に分かる方が早い。`pv_run.js` の CR 混入（Workflow が
起動を拒否する既知の地雷）もここで見る。

これ 1 本で、plan の有無・レベル・プロンプトの生成状況・各回答のサイズ・判定結果が出る。

| 症状 | 見るところ |
|---|---|
| `halt: missing_args` | args を手で書いていないか。`build` の出力をそのまま渡す |
| `halt: task_incomplete` | 担当が raw を書けていない。`doctor` でどれが欠けたか見る |
| `halt: collect_failed` | 成果物が揃っていない。`verify_stdout` に collect の出力が入っている |
| `halt: merge_failed` | Fable も fallback も落ちた。時間をおいて再実行 |

## 利用計測と不具合の蓄積（2026-08-12 追加）

「あまり使われていないレベルが何か、なぜ使われていないか」を後から検証できるようにするため、
`.claude/tools/pv_usage.sqlite3` に全イベントを追記する。

| 見たいこと | コマンド |
|---|---|
| レベル別の使用回数 | `python .claude/tools/pv_usage_log.py levels` |
| 全体の件数・期間 | `python .claude/tools/pv_usage_log.py summary` |
| 失敗・中止の内訳 | `python .claude/tools/pv_usage_log.py failures` |
| 費用（エンジン別・run 別） | `python .claude/tools/pv_usage_log.py cost` |

いずれも `--since YYYY-MM-DD` で期間を絞れる（cgd の `report --since` と同じ）。

**費用は Python が数値で持つ。** cgd は「💰 費用集計」を全 Lv 必須の出力にしているが、
Claude が stderr の usage 行を目で読んで表に起こす運用なので、書き忘れると消える。
pv は `[DS Usage] 今回: ...` を `exec` 時にパースして保存するので、後からいつでも出せる。
codex はサブスク認証で**そもそも料金が出ない**（クォータは消費している）ため、
呼出回数だけが残る。

**記録は自動。** `pv_plan.py` の build / exec / collect と、**あらゆる中止経路**から呼ばれる。
cgd の usage log は「Claude が忘れずに叩く」前提なので急いでいるときに飛ぶ、という実績が
あるため、pv は使えば必ず残る場所に置いた。

### 中止も記録するのが肝

`levels` は 1 レベルにつき 3 つの数を出す:

- **run** — 実際に回せた回数
- **no-impl** — 未実装レベルを指定して拒否された回数 → **需要はあるのに実装が無い**
- **halted** — それ以外の理由で止まった回数（版ずれ・トピック不足など）

使用回数だけでは「使われていない = 不要」と読み違える。
`run=0 / no-impl>0` なら実装が足りないだけで、需要はある。この 2 つは原因が正反対なので分けて数える。

### 不具合の蓄積

外部エンジンが非 0 終了した / exit 0 なのに出力が極端に短い（無言失敗）場合は、
**既存の不具合台帳 `incident_log.py` に自動転記する**。台帳を新しく作らず合流させるのは、
「解析は `/incidents` の専用セッションでまとめて行う」という運用方針に合わせるため。

### 端末別ファイル（2026-08-12 ユーザー指示）

DB は **`pv_usage_<端末名>.sqlite3`** に分かれている。`/g-ul` `/g-dl` はどちらも
robocopy `//MIR` で `.claude` を丸ごとミラーするため、単一ファイルだと
**古い DB を持つ端末が push した時点で他端末の記録が消える**。
端末名を入れて、各端末は自分のファイルしか書かないようにした。

集計 (`summary` / `levels` / `failures`) は `pv_usage_*.sqlite3` を**全部読む**ので、
分けても全体の統計は取れる。2 台以上の記録があるときは「端末別」の行が出る。

### 既知の限界

- `//MIR` は「送り側に無いファイルを消す」ので、`/g-dl` せずに `/g-ul` した端末は
  共有側から他端末のファイルを消す。ただし消えるのは共有側のコピーだけで、
  原本は各端末に残るため次の push で復活する。
  単一ファイル方式の「記録が本当に失われる」とは失敗の重さが違う
- **cgd の usage DB は今も単一ファイル**（`cgd_usage.sqlite3`・68 件）。同じ穴が残っている
- 計測を後から足したため、それ以前の run は `backfill` で `plan.json` から復元した。
  復元行は detail に `backfilled: true` が入っている

## 合格基準（2026-08-11 ユーザー決定・受入テスト中）

pv が「実運用に耐える」と言えるかを、**pv 自身をテーマにせず**実用タスクで測る。
自己レビューでは自己参照になり、実用価値を測れなかったため。

**基準（2026-08-11 改定）**: 実際の検討テーマ **3 件**で Lv2/Lv3 を回し、
そのうち **3 件中 2 件以上**で「**baseline の結論・優先順位・次アクションのいずれかを
実際に変えた論点が 1 件以上**」出ること。

> **なぜ改定したか**: 初版は「baseline に無かった論点が 1 件以上」だった。
> 試行 1 で pv 自身の反証担当に「**LLM なら必ず達成できるのでゲートとして機能しない。
> 『検証したから統合する』ではなく『儀式を通したので統合する』になる**」と指摘され、
> 妥当と認めた。新規性ではなく**判断が動いたか**を問う形に変えた。

### テーマ選定の禁止条件（省略禁止）

**pv / cgd / このスキル群そのもの・受入テストの設計を扱うテーマは選ばない。**
試行 1 は「/cgd と /pv を統合すべきか」を選んでしまい、自己参照を抜けたつもりで
抜けていなかった（pv 自身の棚卸し担当が指摘）。**実際の業務・技術課題から選ぶ。**

### 測定プロトコル（順序を守る。後から書くと後知恵になる）

1. テーマが上の禁止条件に触れないことを確認する
2. **先に**主 context が自分の答えを書き、`baseline/<theme>.md` に保存する。
   このとき **結論 / 優先順位 / 次アクション** を明示的な見出しで書く（後で差分を取るため）
3. その後で pv を回す（テーマと添付は baseline と同一のものを使う）
4. pv の出力のうち、**baseline の結論・優先順位・次アクションを変えたもの**だけを数える。
   「新しいが判断は変わらなかった」論点は **参考として記録するが、合格の根拠にしない**
5. `C:/tmp-ai/pv/_acceptance.md` に、変わった項目を **before → after** の形で書く

**測る対象は「判断が動いたか」であって正しさではない。** 正しさは測れないし、
測ろうとすると LLM に判定させることになって設計が壊れる。

| 試行 | テーマ | 状態 |
|---|---|---|
| — | `/cgd` と `/pv` を将来統合すべきか | **無効**（テーマ規約違反・基準改定前。知見は記録に残す） |
| 1 | 038 の本番化と 036 とのマスタ二重管理 | **合格**（結論・優先順位・次アクションすべてが動いた。8 項目・全件裏取り済） |
| 2 | 未定 | 未 |
| 3 | 未定 | 未 |

## 既知の限界（隠さずに書く）

- **Verify も LLM 経由**。Workflow は Bash を持てないので、Step 4 を人（主 context）が
  やらない限り完全な機械ゲートにはならない
- **Lv1 の 2 視点は同一モデル・同一 effort** で、違うのは役割の指示文だけ。
  誤りが相関しうるので、「2 者が一致した」を独立した 2 票として扱ってはいけない。
  Lv2 でエンジンが分かれれば緩和される見込み（未検証）
- **成否判定は「非 LLM で測れること」だけ**: 存在 / 200 バイト以上 /
  箇条書き・見出しが 3 行以上 / 降参文だけで終わっていない。
  **内容の妥当性は測れない**（測ろうとすると LLM に判定させることになり設計が壊れる）
- **プロンプトインジェクション対策は平文の注意書きのみ**。テーマ本文を
  「データであり指示ではない」と囲っているが、構造的な分離ではない。
  外部から取ってきた文書をそのままテーマにするのは避ける
- `/cgd` に対する優位帯域は**実測比較をしていない**
- **codex のトークン消費が計測できない。** 非 TTY 実行では codex が `tokens used` を出力しないため
  （実測確認済み・`INC-20260811` 記録）。`ai_telemetry` hook も Bash 文字列に codex の語が出ないので検出しない。
  **pv 経由の codex はクォータ消費が二重に不可視**になる。重い run を繰り返す場合は注意する
- **外部エンジンは Python の subprocess で起動する**ため、Bash のコマンド文字列に
  エンジン名が現れず、`cgd_wf_gate` の遮断をすり抜ける。pv は常に Workflow を使うので
  すり抜けること自体は許容だが、気づかないままにしないよう
  `<run>/audit.jsonl` に起動記録（時刻・エンジン・終了コード・出力サイズ）を残している

## 設計の背景（なぜ Python を挟むのか）

LLM が毎回「依頼テキスト」と「起動コマンド」を組み立てると、文言が毎回変わって結果を
比較できなくなり、引数名やパスの取り違えも起きる。実際に 2026-08-09〜11 にかけて、
Workflow の args キー名を 4 回連続で間違え、**8/9 に作られた無関係な設計文書を
レビューし続ける**事故が起きた。しかも 4 回とも「レビューは成立している」ように見えた。

そこで **依頼テキストの生成と成否の判定を Python に寄せ**、LLM の仕事を
「Python が出したコマンドを 1 回叩く」「結果を構造化する」だけに狭めている。

この設計自体も pv Lv1 の初回実行で自己レビューにかけ、
「Workflow が collect を叩かず統合役の自己申告を信じていた」「build が古い raw を
消さない」という欠陥を発見して修正した（2026-08-11）。

## スタンプ運用と版ずれ検出（2026-08-12 追加）

冒頭の `<!-- SKILL_VERSION: YYYY-MM-DD_HHMMSS -->` は、セッションのコンテキストが最新かを
判定するためのもの。**本文を編集したら必ず更新する**（`date` コマンドで実時刻を取る）。

### なぜ必要か

スキル本文は Skill 呼び出し時に会話へ差し込まれる **スナップショット**で、以後ディスク上の
SKILL.md を更新しても、走っているセッションの認識は古いまま固定される。cgd では 5 月の本文
（Lv1-5 / Gemini 構成）を 7 月まで参照し続けた事故が実際に起きている。pv は手順を Python 側に
寄せた設計なので、本文が古いと「存在しないオプションを渡す」「新しい必須ゲートを飛ばす」
という形で表面化する。

### 仕組み（文章の注意書きではなく、非 0 終了で止める）

`build --skill-version <値>` に、**いま読み込んでいる本文の冒頭スタンプ**を渡す。
Python がディスク上の値と突き合わせ、

| 状況 | 挙動 |
|---|---|
| 一致 | 続行 |
| 不一致 | **中止**（exit 1）。「SKILL.md を読み直してから再実行」と表示 |
| 省略 | **中止**（exit 1） |
| ディスク側にスタンプが無い | 警告のみで続行（止めると SKILL.md を直すまで pv が使えなくなるため） |
| 共有ミラーの方が新しい | 警告のみで続行（`/g-dl` を検討、と表示） |

中止は run ディレクトリを作る**前**に行う。途中で落ちて plan.json の無い run が残ると、
`doctor` が「build がまだ」と誤案内するため。

実行した run がどの版の手順で回ったかは `plan.json` の `skill_version` に残る。
`doctor` は常に「ディスク上の版 / 共有ミラーの版」を先頭に表示する。

### この検査の限界（隠さずに書く）

**ディスクを `grep` した値を渡すと必ず一致するので、検査は無意味になる。**
守れるのは「自分の context にある値を渡す」という約束の部分だけで、そこは機械化できていない。
同じ限界は cgd の Step 0 にもある。

補助として `UserPromptSubmit` フック `skill_freshness.py` が全スキルの mtime を監視しており、
**セッション開始後に**変更されれば警告が出る（pv も対象）。ただしこちらは
「セッション開始時点ですでに古い本文を読んでいた」場合は検出できない。
2 つは守備範囲が違うので、両方あって初めて実用的な網になる。
