# /toms-web — TOMS WEB 注文の自動操作（確認画面まで）

tshirt-order スキルが作った TOMS 用 CSV（`017.Tシャツなどの注文\toms_csv\*.csv`）を、
Claude in Chrome で TOMS の WEB 注文に取り込み、**注文内容確認画面で止める**スキル。

- 対象サイト: `https://store.tomswear.com/`
- 使うブラウザ: **Claude in Chrome**（`mcp__claude-in-chrome__*`。deferred なら ToolSearch で先に一括ロード:
  `select:mcp__claude-in-chrome__tabs_context_mcp,mcp__claude-in-chrome__navigate,mcp__claude-in-chrome__computer,mcp__claude-in-chrome__read_page,mcp__claude-in-chrome__find,mcp__claude-in-chrome__get_page_text,mcp__claude-in-chrome__file_upload,mcp__claude-in-chrome__tabs_create_mcp`）
- 画面の観察記録（2026-10-09 実機）: `094.Chrome自動操作\docs\toms_web_screens.md`

## ★ 標準の手順: 端末 A のスクリプトに依頼する（2026-10-18 以降）

TOMS の注文は、**端末 A の Playwright スクリプト `C:\ClaudeCode\900.ClaudeCode	oms_order\`（A の README.md 参照）が標準**。TK の Chrome 拡張での 1 画面ずつの操作（下の「手順」）は遅いので、**A が使えないときの予備**にする。確認画面まで約 1 分。

**TK がやること（質問は最初にまとめて聞く。ルールは下の「質問は最初にまとめて聞く」のとおり）:**
1. 納品先（セブンエス／ステッチハウス／サスガワークス／アドプロセス）・運送会社・出荷予定日・早割貯打を、最初に聞く（依頼文で決まっていれば聞かない）。
2. **申請 JSON と発注 CSV を、relay の添付で A へ送る**（`--to A`）。
   ```
   {"source":"TK","csv_path_or_content":"<CSV のファイル名>","destination":"セブンエス","carrier":"yamato",
    "ship_date":"2026-10-19","early_bulk":true,"mode":"review_only","expect":{"lines":4,"total_qty":200,"subtotal_yen":58000}}
   ```
   - CSV は 6 列・ヘッダー 1 行・100 行以内・同じ品番/カラー/サイズの重複行は不可（CP932 可）。
   - `expect` は、CSV から数えた行数・合計枚数・合計金額（税抜・割引前）。
3. A が enqueue → run。確認画面で、決定的な検査と DeepSeek の判定を行い、OK なら**運用者の LINE に「注文確定／中止」のボタン**が届く（最大 15 分待つ）。**確定を押すのは運用者**（A のスクリプトの確定関数が、押された後に 1 回だけ押す）。
   - 自動確定（`mode=auto_confirm`）は、A の設定で許可されるまで無効（今は無効）。
   - 上限: 500 枚・税込 200,000 円。同じ CSV+出荷予定日+納品先は 24 時間以内に確定しない。
4. A の結果（`status`: confirmed／stopped／needs_human／failed／cart_not_empty）を待つ（relay の返信）。`confirmed` なら、確定・照合一致。注文詳細の全文は NAS `999.一時ファイル	oms-result_YYYYMMDD_HHMM.txt`。
5. **納品先がセブンエスの無地T（ECM 依頼）なら、確定後に入荷登録の申請**（下の「入荷登録の申請」）。

**TK の Claude は、どの場合も「注文確定」を押さない**（A のスクリプトの確定関数だけが、運用者の承認後に押す）。
**失敗したとき**: `cart_not_empty` は TOMS のカートを空にしてから再申請（取り込みはカートを全消去する）。`failed`／`needs_human` は再申請せず、理由を報告してユーザーに聞く。前回の途中状態が残ったカートは、納品先の欄が出ず failed になる。

## 🚨 絶対ルール

1. **「注文確定」ボタンは Claude が押さない。** 確認画面で止まり、金額・内容を報告して、ユーザーに押してもらう。確定後のキャンセル期限は 10 分。
2. **ID / パスワードは入力しない。** ログイン画面はブラウザのオートコンプリートで入力済み。Claude は「ログイン」ボタンを押すだけ（下記の注意参照）。入力欄が空ならユーザーに手動ログインを頼む。
3. **TOMS を同時に複数タブで操作しない**（サイトの注意書き。注文データが壊れる）。Claude の作業タブ 1 つだけで進め、ユーザーの別タブで TOMS が開いていれば先に閉じてもらう。
4. **CSV 取り込みはカートを全消去する。** 取り込み前にカートの件数（ヘッダーのカート数字）を確認し、0 でなければ「カートの中身が消えます」とユーザーに確認する。
5. 納品先・運送会社・出荷予定日は **既定値を提示してユーザーに選ばせる**（黙って既定値で進めない）。サイトには前回の選択が残っているため、毎回こちらで明示的に設定し、確認画面で突き合わせる。
6. **質問は、最初に（ブラウザ操作より前に）まとめて聞く。** 下の「質問は最初にまとめて聞く」に従う。

## 🙋 質問は最初にまとめて聞く（2026-10-16 ユーザー指示・必須）

ユーザーは、依頼を出したあと**席を外す**。画面操作の途中で質問すると、答えが来るまで TOMS のセッションが切れて、取り込みからやり直しになる（2026-10-16 実例）。したがって:

1. **依頼を受けたら、最初のターンの最初の操作で、必要な質問をすべて一度に聞く。** CSV の取り出し・ログイン・取り込みなど、**何かを始める前**に聞く。聞いてから、回答を待たずに作業を始めない（答えが決まっていない項目に依存しない部分だけは、質問と同時に進めてよい）。
2. 質問は **AskUserQuestion（クリック形式。最大 4 問）** にまとめる。聞くこと（依頼文や過去の指示で決まっているものは聞かない。決まっていることは「以下で進めます」と 1 行で伝えるだけにする）:
   - **納品先**（セブンエス（既定）／サスガワークス／アドプロセス／その他）
   - **運送会社**（ヤマト運輸（既定）／佐川急便）
   - **早割貯打**（希望する（既定）／希望しない）※出荷予定日が翌営業日以降のときのみ。当日出荷なら項目自体が無い
   - **出荷予定日**（依頼に書かれていなければ。**土日祝は選べない**ので、依頼の日付が土日祝なら、その場で代わりの平日の候補を出して聞く。例: 日曜なら翌月曜）
   - カート内容が消えてよいか（カートが 0 でない場合。0 のことが大半。ログイン後でないと分からないので、**わかった時点で**聞く）
3. **回答済みの項目は、やり直しになっても再質問しない。** セッション切れ・タブ固まり・取り込み失敗でやり直すときは、前の回答をそのまま使う（変えたいときだけユーザーが言う）。回答は台帳（ctx）の STATE に 1 行で残す。
4. 画面操作の途中で新しい疑問が出たら、**止まらずに既定値で進めて確認画面まで行き**、確認画面の報告に「判断した点」として書く（確定前なので、ユーザーが見て直せる）。**例外**: 金額・数量・納品先など、間違うと取り返しがつかないものだけは止めて聞く。
5. 確認画面に着いたら、**まとめて 1 回だけ**報告する（途中経過の長い報告で待たせない）。

## ⏱ 待ち時間ルール（2026-10-09 ユーザー指示・必須）

**TOMS のサイトは非常に反応が遅い。ボタンが画面に出ていても、押した直後は反応しないことがある。**

- **次の操作の前に、最低 3 秒待つ。** 特に次の直後:
  - `file_upload` でファイルを渡した直後 → 「取り込み」を押す前に 3 秒以上待つ（待たずに押すと無反応。実例: 2026-10-09 G1849、1 回目は無反応で 2 回目に成功）
  - ページ遷移（ログイン・取り込み・注文する・確認へ・戻る）の直後 → 描画（白画面）が終わるまで待つ
  - ラジオ・チェック・日付の選択の直後 → 画面が更新されるまで待つ
- ボタンを押したのに画面が変わらないときは、**まず待つ → スクリーンショットで確認 → それでも変わらなければ 1 回だけ押し直す**（連打しない。二重送信の恐れがある確定系のボタンは、押し直し前に必ず状態を確認する）。
- `computer` の `wait` は最大 10 秒。長い場合は複数回に分ける。

## 手順

### 0. 事前チェック（CSV）と、最初の質問
- **最初に**「質問は最初にまとめて聞く」の質問を済ませる（AskUserQuestion）。回答が来てから、以下に進む。
- 対象 CSV のフルパスを確認（直近の `toms_csv\YYYYMMDD_件名_TOMS.csv`。複数候補ならユーザーに選ばせる）。
- 形式: UTF-8 または CP932、ヘッダー 1 行 + 明細。列 = 品番(5桁), カラーコード, サイズコード, 数量, 備考(20文字以内), お客様注文No。
- **明細 100 行以内**（超えたら分割して再取り込み）。数量の合計を控える（後で照合）。
- tshirt-order の黒/白コード事故（001=白/005=黒）に注意: 件名とカラーコードの食い違いがあれば取り込み前に指摘。

### 1. ログイン
1. `tabs_context_mcp`（createIfEmpty）→ 作業タブを決める。
2. `https://store.tomswear.com/sca-dev-2021-2-0/checkout.ssp?is=login&login=T#login-register` を開く。**描画に数秒かかる**（初回は白画面。4〜5 秒待つ）。
3. すでにログイン済みなら（ヘッダーに「ようこそ 株式会社制服のフジ」）スキップ。
4. 入力欄（メール/パスワード）が自動入力されているのをスクリーンショットで確認し、**`find` で「ログイン」ボタンの ref を取って ref 指定でクリック**。
   - ⚠ 座標クリックでは 1 回目に通らなかった（2026-10-09）。ref 指定なら通る。通らなければもう一度 ref クリック。
   - それでも進まない／入力欄が空 → ユーザーに手動ログインを頼む。

### 2. CSV 取り込み
1. カート数を確認 → 0 以外ならユーザーに確認（ルール 4）。
2. `https://store.tomswear.com/csv-order` を開く。
3. `find` で「ファイルを選択」(file input) の ref を取り、`file_upload` で CSV を渡す。**ファイル選択ボタンは絶対にクリックしない**（OS ダイアログは操作不能）。
4. `find` で「取り込み」ボタンの ref → クリック。数秒待つと「CSVカート」画面（`…#shippingoptions`）へ自動遷移。
5. `get_page_text` で明細を読み、**CSV と照合**: 行数・品番・カラー・サイズ・数量・合計数量・合計金額。不一致や在庫不足があれば、ここで止めて報告。
   - 取り込めない/エラーなら、画面の文言をそのまま報告。100 明細超なら分割を案内。

### 3. ご注文情報入力（ステップ 2）
1. カート画面の「注文する」(ref を find) をクリック → `…#opc`。これは確定ではなく次の入力画面へ進むボタン。
2. 納品先・運送会社・出荷予定日・早割貯打は、**手順 0 の最初の質問で答えが決まっている**。ここでは聞かず、その回答で入力する（再質問しない）。
3. 画面は縦に長い。**納品先・出荷主の一覧は内側スクロール**なので、ページ全体をスクロールするときはマウスを一覧の外（右余白 x≈1400）に置く。
4. 設定する項目（選択後は必ず再読込して値を確認）:
   - 納品先: カードのラジオ「選択」。選択済みのカードが「選択済」表示になる。
   - 運送会社: 「佐川急便 / ヤマト運輸」ラジオ。
   - 出荷予定日: 入力欄をクリック → カレンダー（英語表記）から日付をクリック。選べない日は灰色。日付を入れると「早割対象です」と割引額が出ることがある。
   - 個別包装・副資材（OPP 袋）は既定の「不要/しない」のまま（指示がない限り変更しない）。
5. 「ご注文内容確認」ボタン（ref を find）をクリック。出荷予定日が未入力だと「出荷予定日を入力してください。」の赤エラーが出てステップ 2 に留まる。

### 4. 注文内容確認（ステップ 3）で止まる
1. `get_page_text` + スクロールで確認画面の全体を読む。
2. ユーザーへ報告（表にする）:
   - 明細（品番・カラー・サイズ・数量・単価・明細金額・お客様注文NO・備考）と CSV との一致
   - 金額: お買い上げ合計 / 早割 / 配送料 / 合計(税抜) / 消費税 / **合計(税込)**
   - 納品先 / 出荷主 / 運送会社 / 送料支払い / 土曜・日祝配送 / 早割貯打 / **出荷予定日**
3. **出荷予定日 > 納期（発注書の納期）なら警告**し、TOMS 側で修正してよいかユーザーに確認（tshirt-order の規則）。
4. 「**画面の『注文確定』ボタンをご自身で押してください**」と伝えて終了。**Claude は押さない。**
5. **確定後の即時検証（必須・2026-10-09 ユーザー指示）**: ユーザーが「確定した」と伝えてきたら、**すぐに**同じタブの完了画面（ステップ 4）を `get_page_text` + スクリーンショットで読み取り、直前に報告した確認画面の内容と突き合わせる。
   - 照合項目: 受注番号の有無（`#`+8桁が不変条件。memory「トムス受付番号」）/ 合計金額（税込）/ 明細数と合計数量 / 納品先 / 運送会社 / 出荷予定日 / 土曜・日祝配送 / 同梱 / 備考（午前中着指定）
   - 完了画面が出ていない・エラー・二重表示などの異常は、**そのまま報告**して、キャンセルするか確認する（確定後 **10 分以内ならキャンセル可能**。キャンセル操作自体は注文履歴から行う想定で、ユーザーの承認を得てから）。
   - 異常なしなら「正しく注文されています」と一致項目の表を返す。
   - 確定前に画面を閉じない・リロードしない（完了画面を読み取れなくなる）。

## キャンセル手順（確定後 10 分以内）

## 入荷登録の申請（ECM 依頼の無地Tシャツ・確定後。2026-10-17 追加）

ECM「Tシャツ注文」から出た依頼（7S＝セブンエス宛て・CMR の入荷予定の登録が要るもの）は、注文確定・検証のあとに、**ECM の受付口へ「登録の申請」を出す**。**CMR の API や ECM の既存の登録 API（貼り付けルート。LAN は PIN 不要）は直接叩かない**（A 端末の方針。誤登録の取り消しが CMR 管理画面での人の操作になるため）。

1. 注文詳細の全文を `toms-result_YYYYMMDD_HHMM.txt` に保存済みであること（上の手順）。
2. `python C:\ClaudeCode\094.Chrome自動操作\ecm_arrival_client.py submit <toms-result_….txt>`
   - 申請は、ECM が 2 系統（DeepSeek＋コード）で解析・検証し、問題なければ**承認待ち（pending_approval）で保留**される（CMR へは送られない）。入荷予定日は出荷予定日の翌日をサーバーが計算する。
   - キーは `C:\Users\jl4lv\.ecm\api_key.txt`（値は表示・記録しない。無ければユーザーに発行を頼む）。
3. 結果を表で報告する: request_id・status・受注番号・出荷予定日・入荷予定日・明細（CMR 品番と数量）・合計・警告・precheck。
   - `rejected`（解析不一致・商品マスタに無い・登録済み など）は、理由をそのまま伝えて止まる。**勝手に再申請・別経路での登録をしない。**
4. **承認はユーザーが A 端末の ECM 画面（無地T在庫管理 → Tシャツ注文 →「📨 AIからの入荷登録申請」）で、原本と見比べて PIN を入れて行う。Claude は承認できない。** 承認後の状態確認は `ecm_arrival_client.py show <request_id>`（registered になり、CMR の受付・検証の結果が付く。`accepted` は受付だけで、`verified` が true で確認完了）。
5. 承認待ちは 72 時間で取り下げ扱い。取り下げは `cancel <request_id>`（承認待ちのときだけ）。
- **明細を限定して登録する（2026-10-18 追加）**: 同じ入荷予定日に、別の受注番号が同じ品番を登録済みで、ECM が却下したとき（例: #56149955 の BK-3L・BK-L が #56146432 と重複）、重複する明細だけを運用者が CMR 管理画面で既存の指示へ加算し、**残りだけを ECM に申請する**。
  `python ...\ecm_arrival_client.py submit <toms-result_….txt> --only-items 300ACT-NV-M 300ACT-NV-S --note "BK-3L/BK-Lは運用者がCMRで加算"`（除外で書くなら `--exclude-items ...`）。
  - `--note`（理由）は必須（200 字以内・改行なし）。限定しないのに note だけは不可。
  - 除外した明細は「運用者が手動対応」として記録される。**限定して登録した注文の「残り」を、後から ECM で登録することはできない**（受注番号単位の二重登録ガード。409）。
  - 入荷予定日は、出荷予定日の翌日のまま変えない（ユーザー決定）。
  - A の ECM の本番反映（サーバー再起動・キャッシュ版数更新。運用者の承認が要る）の**連絡を待ってから**申請する（反映前は only_items/note が黙って無視され、注文全体の申請になる）。
- 警告に「発注数と履歴の数量が違う」が出たら、**ECM の発注記録に数量修正前の途中版が残っているだけのことが多い**（2026-10-16 の実例）。TOMS の注文が正しいかは、依頼の内訳と突き合わせてから判断する（勝手に差を許容しない。ユーザーに伝える）。

## よくある失敗

- **「ログインセッションが切れました」ダイアログでタブが固まる（2026-10-09）**: ネイティブの `alert` がページ全体を止め、`find`・`screenshot`・キー入力（Return）も効かなくなる（CDP がタイムアウトする）。computer-use は **ブラウザに「見るだけ」権限しか付けられず、OK ボタンを押せない**（request_access を試さない）。**対処: 固まったタブを `tabs_close_mcp` で閉じ、`tabs_context_mcp {createIfEmpty:true}` で新しいタブを取り直して、ログインからやり直す。** ユーザーが画面で OK を押せる場合は、それでもよい。
- **セッション切れは、時間が空いたあとに起きる**。しばらく操作していなかった場合は、最初に `csv-order` を開いてログイン状態を確認する。**質問で長く待たせたために切れた実例（2026-10-16）があり、質問は最初にまとめて聞く**ルールを作った。切れて取り込みからやり直すときは、**前の回答をそのまま使って**再質問しない。
