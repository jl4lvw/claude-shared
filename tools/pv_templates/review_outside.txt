この変更の経緯を知らない立場で、添付された差分を読んでください。

## 進め方
1. **前提を知らないと分からない箇所**を名指しする（読んで意図が取れない差分は、それ自体が問題）
2. 規約・慣習からの逸脱を指摘する（命名、エラーの扱い方、ログ、文字コード、パスの扱い）
3. 同じ意味の処理が別の書き方で増えていないか
4. テストが必要なのに無い箇所
5. 「動くが後で困る」ものを挙げる

## 注意
- 内輪の事情を推測して擁護しない。**読んで分からないものは分からないと書く**
- 好みの問題（フォーマット・些細な命名）は severity を `minor` にとどめる

## 出力形式（**厳守**・機械照合します）

指摘は **JSON** で出してください。本文の最後に、次のフェンス付きブロックを 1 つだけ置きます。

```json
[
  {"finding_id": "<担当id>:1", "severity": "critical", "file": "<差分に出てくるパス>",
   "side": "new", "line": 123, "title": "<1 行要約>", "rationale": "<なぜ問題か・何が壊れるか>"},
  {"finding_id": "<担当id>:2", "severity": "minor", "file": "...", "side": "file",
   "title": "...", "rationale": "..."}
]
```

- `severity` は **`critical` / `major` / `minor` のいずれか**（絵文字や HIGH 等は使わない）
- `side` は `new`（変更後の行）/ `old`（削除された行）/ `file`（ファイル全体の話）
- `line` は `side` に対応する行番号。ファイル単位の指摘なら **省略**して `side": "file"` にする
- `file` は **差分に出てくるパス**を書く。差分に無いファイルへの指摘は機械的に弾かれます
- `finding_id` は担当 id と連番（例 `bug:1`）。**重複させない**
- 指摘が無ければ空配列 `[]` を出す。**無理に絞り出さない**

JSON の前に、人が読む要約を数行書いて構いません（採点対象は JSON です）。

## 注意
- **差分に無いファイルの話は書かない。** 呼び出し元など差分外の行に触れるのは構いませんが、
  ファイル自体は差分に含まれている必要があります
- 推測で行番号を作らない。分からなければ `side": "file"` にする
